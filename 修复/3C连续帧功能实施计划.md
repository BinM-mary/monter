### 修订结论：四项 P0 缺口

| 缺口 | 核查结论 | 本文定案 |
|---|---|---|
| 总截止混用 | 当前只接受 SF，尚无正在运行的多帧发送；但直接沿用首帧 t0＋5 s 会使长请求发送途中超时 | 多帧拆分发送阶段截止与响应阶段截止，详见 §4.3 |
| 回显与响应同构 | 属实。相同 NAD 无法区分；未匹配当前回显的旧 FF/CF 可能污染响应 TP | 增加阶段判定表、已发送回显历史、固定隔离窗口及不可判别边界，详见 §4.5 |
| 不发 3D 与提前读取 NRC 冲突 | 属实。当前接口下从机需获得 3D 读取机会才能返回诊断数据 | 本版选择发送期间不发 3D，明确接受无法提前读取 NRC，详见 §4.6 |
| BeginReceive 过早 | 属实。当前在请求发送前启用 TP，多帧直接复用会扩大污染窗口 | 多帧仅在请求发送及隔离完成后 BeginReceive，发送阶段禁止投递 TP，详见 §4.7 |

以上是实现方案的强制约束。间隔、窗口和时限的具体数值仍需中间件与 Bootloader 契约确认，不能用未经验证的默认值填补。

第二轮补充定案：测试设施与同源时钟列为 P0，测试工程必须在仓库外临时创建并在测试后删除；结果进度、失败枚举、参数归属和多帧验证入口按 §4.8～§4.11 实施。本轮仍仅修改本文，不创建测试工程、不修改代码。

第三轮补充定案：临时工程默认采用普通 net10.0＋生产源码显式白名单，排除 WPF 日志实现与视图层；取消入口固定为 ExecuteAsync(request, cancellationToken = default)，排队时即响应；发送失败及协议归属异常默认中止整批并清空队列，普通 ResponseMismatch 仅结束本笔。具体规则见 §4.4、§4.8、§4.11。

第四轮补充定案（覆盖上文相应的历史修订摘要）：长请求彻底忽略 SF Timing；FailedPhase 使用明确枚举；响应超时或不匹配后能否继续必须经过跨事务归属门禁，缺少可靠隔离契约时选择保守失败，不能默认继续。详见 §4.4.2、§4.9.1、§4.10 与 §7.5。

第五轮补充定案（覆盖第四轮中过宽的表述）：负响应本阶段不解析，且**不构成归属异常**；跨事务门禁只在“前一笔异常结束、可能仍有未归属数据”时关闭，收到完整但不匹配的响应不关闭门禁。新增 `DiagnosticGateClosed` 区分“诊断已锁止”与“排队被取消”，并定义最小解除途径。详见 §4.4.1、§4.4.2、§4.9.2 与 §7.5。

第六轮补充定案（实施后修订，覆盖第五轮中仍过宽的部分）：**单纯超时不再关闭跨事务门禁**，只在 `ProtocolAttributionError`、响应阶段取消、带在途请求断线三种“确有陈旧字节证据”的情况下关闭。原因是门禁没有界面解除入口，一次设备无应答就会让整轮诊断必须重启应用；而超时时设备本就未应答，迟到响应概率极低。残余风险与升级前必须重新评估的边界见 §4.4.2。

## 1. 当前能力与功能目标

### 1.1 当前实现

| 场景 | 当前支持情况 |
|---|---|
| 多笔独立诊断：每笔发送一个 3C，读取 3D，完成后执行下一笔 | 已有 FIFO 排队机制 |
| 一条长请求：连续发送 3C 首帧和连续帧，全部发送后读取 3D | 尚未实现 |
| 3D 多帧响应 | 已实现 SF/FF/CF 接收及重组逻辑，实机效果仍需联调验证 |

当前请求编码仅支持 1～6 字节 UDS 消息；每笔事务发送一次 3C 后即启动 3D 轮询。因此，不能把 FF、CF 分别加入现有诊断队列来代替长请求发送。

### 1.2 目标流程

```text
提交完整 UDS 请求
    ↓
校验参数、保存请求快照
    ↓
进入诊断独占，暂停应用帧
    ↓
按长度生成 SF，或 FF + 多个 CF
    ↓
按规定顺序、间隔和回显规则发送全部 3C
    ↓
全部分片写入并确认 → 固定回显隔离窗口 → 初始化响应 TP → 轮询 3D
    ↓
复用现有响应重组和业务验证
    ↓
结束事务，执行下一笔或恢复应用通信
```

具体目标：

- 保留现有 1～6 字节单帧请求能力。
- 增加长请求分包、连续发送、序号回绕、末帧填充。
- 一条请求的全部 3C 分片作为一个事务执行，不拆成多个独立诊断业务。
- 多帧请求发送及回显隔离期间不插入应用帧、其他诊断事务或任何 3D 读取；因此不能提前读取 NRC，明确接受的代价见 §4.6。
- 中途写入失败、回显异常、超时或断线时，停止后续分片并明确返回失败原因。
- 保持三个版本读取及现有 3D 多帧响应功能兼容。

### 1.3 适用范围与后续工作

本次实现诊断传输能力。固件文件解析、升级会话、安全访问、下载块协商、擦写、校验、重启等属于后续升级业务。多帧 3C 功能完成，不等于完整升级功能完成。

负响应（`7F`）的结构化解析与处理不在本阶段范围：收到时按 `ResponseMismatch` 报告，不新增 NRC 语义，也不据此关闭跨事务门禁（§4.4.2）。

一条长请求的独占与整个升级流程的独占应分别设计。未来升级由多个先后提交的 UDS 事务组成时，队列短暂清空可能恢复应用通信；升级业务阶段需要增加具有明确生命周期的批次独占机制。

## 3. 实施前需要确定的协议决策

以下内容尚未在现有多帧请求契约中确认，不能直接沿用单帧请求时间规则。

| 决策 | 建议方向 | 需要确认的依据 |
|---|---|---|
| 每帧是否必须等待回显 | 本版按“发一帧、确认一帧”设计（§4.3）；中间件不支持时先修订方案再实施 | 中间件是否每帧可靠回显，等待回显是否满足从机连续帧接收时间要求 |
| 相邻 3C 发送间隔 | 使用独立配置，明确起点，超时后不集中补发 | 中间件吞吐、LIN 波特率、Bootloader 连续帧要求 |
| 回显含义 | 区分串口写完、中间件反馈、LIN 总线发送完成 | 中间件协议或源码 |
| 响应阶段起点 | 本版多帧采用最后一帧写入和有效回显均完成的事件；截止算法固定见 §4.3 | 确认逐帧回显可用及其时延；不得仍从第一帧写完计算响应截止 |
| 首次 3D 时机 | 请求序列发送结束后启动，与周期独立配置 | Bootloader 处理时间和接口约定 |
| 最大请求长度 | 分别约束编码上限和设备接收上限 | Bootloader 缓冲区、下载块长度及请求开销 |
| 中途失败后恢复 | §4.4 默认中止整批、清空后续队列，在途写入收尾后恢复应用通信，不自动重发 | 阶段 0 必须确认是否增加恢复窗口，以及残留重组时应用帧是否允许恢复、何时接受新诊断 |
| 提前负响应 | 本版发送期间不发 3D，接受无法提前读取 NRC | 确认 Bootloader 提前拒绝后是否保留 NRC、是否容忍后续 CF；若不兼容则阻塞当前方案 |
| 回显隔离窗口 | 固定长度、不被新回显延长，且计入响应预算；详见 §4.5 | 中间件最大回显迟到时间、顺序保证及同字节响应的归属依据 |

串口写入顺序正确，不能证明 LIN 总线帧间隔正确。最终时间参数必须结合中间件能力和总线抓包验证。

如果中间件要求流水发送，应设计有界的待确认分片集合，不能简单改为不等待回显的循环。

## 4. 关键设计方案

### 4.1 请求分包

沿用项目现有 TP 接收格式，为发送侧增加独立、无串口依赖的分包方法。

| UDS 消息长度 L | 分包方式 |
|---|---|
| 1～6 字节 | 一个 SF |
| 7～配置上限 | 一个 FF，随后若干 CF |
| 0 或超过上限 | 入队前拒绝，不产生发送副作用 |

编码规则：

- FF 携带完整 UDS 消息长度，首帧装入 5 字节消息。
- CF 每帧装入最多 6 字节，序号从 1 开始，按 4 位回绕。
- 每个 PDU 均为 8 字节，末帧未使用位置填 `0xFF`。
- 消息长度不包含 NAD、PCI、填充和 LIN 校验。
- 每个 PDU 分别通过现有 `CreateDiagnosticRequest()` 封装和计算经典校验。
- 按现有 12 位长度格式，编码上限可设为 4095 字节；设备允许值可更小。

对于 `L > 6`：

```text
分片数 = 1 + 向上取整((L - 5) / 6)
```

提交时复制 UDS 请求和响应匹配规则，避免调用者在排队期间修改数组。

### 4.2 事务状态机

```text
排队 → 获取独占 → SendingRequest → EchoDrain → WaitingResponse → 收尾
                         ↘ 任一阶段失败/取消/断线 → 收尾
```

发送阶段记录：

- 当前分片索引、总片数。
- 当前预期回显及确认状态。
- 当前写入是否完成。
- 分片间隔与回显截止。
- 本笔事务、连接和计时回调的代次。
- 已实际提交发送的全部分片原始回显、发送时间、确认时间及最后一帧完成时刻。
- 发送/响应截止是否已启用，回显过滤结束时刻及回显隔离结束时刻。

约束：

1. 发送前登记预期回显。
2. 回显早于写入任务返回时先保存结果，不能误判超时。
3. 按 §4.5 处理旧回显；NAD 和经典校验不能单独证明响应归属。
4. 全部请求分片完成且隔离窗口结束后，才启用 TP 并启动响应轮询。
5. 一笔事务只发布一次最终结果，推进一次队列。

### 4.3 时间模型

多帧不得沿用“第一帧写完＋5 s”覆盖发送与响应的总截止。明确拆成两个阶段：

```text
t_send_start = 首个 3C 写入提交前的单调时间（不含排队和获取独占）
SendDeadline = t_send_start + SendBudget(N)

t_last_complete = max(最后一帧写入完成时间, 最后一帧有效回显确认时间)
ResponseDeadline = t_last_complete + ResponseBudget

DrainEnd = t_last_complete + EchoDrainDuration
首次 3D 最早时间 = max(DrainEnd, t_last_complete + FirstResponsePollDelay)
```

本版多帧按逐帧确认设计：最后一帧写完和有效回显都满足才算请求发送完成，二者先后顺序均须支持。该完成事件是软件侧事务锚点，不宣称等于真实 LIN 总线发送完成。若中间件不支持这一确认方式，应先修订协议方案再实施，不能在代码中暗换起点。

发送预算根据片数或显式配置确定。一个保守预算模型为：

```text
SendBudget(N) = N × (WriteBudget + EchoBudget)
                + (N - 1) × InterFrameGapBudget + SchedulingMargin
```

该式仅给出预算构造方式，不决定具体数值；还需满足从机允许的最大相邻帧间隔。若配置固定发送上限，必须在发送前验证它足以覆盖声明支持的长度和发送策略，否则拒绝请求。

4095 字节需要 `1 FF + 682 CF = 683 帧`，并非 683 个 CF。若仅假设相邻帧间隔 20 ms，首尾跨度已约 13.64 s，尚未计入额外等待；这说明固定 5 s 不能作为其发送上限，而不表示已确认使用 20 ms。

截止检查规则：

- `SendingRequest`：只检查 SendDeadline、当前写入/回显截止及可选的有效整笔上限，不检查尚未启用的 ResponseDeadline。
- `EchoDrain`、`WaitingResponse`：检查 ResponseDeadline；隔离等待计入响应预算，不能在首次 3D 时重新起算。
- ResponseBudget 必须覆盖固定隔离窗口、首次读取等待及有效响应接收时间；参数组合不可行时入队前拒绝。
- 接收硬截止和 InspectTimerCallback 使用相同阶段规则，过期回调通过事务代次失效。
- 所有截止使用显式有效标志或可空值；不能让尚未赋值的 0 参与比较。
- 可选整笔总上限不得隐式继承旧 5 s；其预算至少覆盖已约定发送和响应预算，或明确作为主动取消的更短限制。

| 时间约束 | 作用 |
|---|---|
| 单帧写入等待上限 | 防止等待串口任务无期限挂起 |
| 每帧回显等待上限 | 判断该分片反馈是否缺失 |
| 相邻分片发送间隔及允许上限 | 控制节奏，避免从机接收超时 |
| 整条请求发送上限 | 从 t_send_start 起，按片数或显式配置确定 SendDeadline |
| 响应阶段总上限 | 从 t_last_complete 起确定 ResponseDeadline，包括隔离窗口 |
| 响应 CF 的 N_Cr | 复用现有响应重组计时 |
| 可选整笔事务总上限 | 防止发送与响应阶段组合后失去总约束 |

统一使用单调时钟。错过最大允许发送间隔时，应按协议判断失败，不能快速补发所有错过分片。

`FirstResponsePollDelay` 与 `ResponsePollPeriod` 语义分离：多帧按 §4.10 使用前者决定首次 3D、后者决定轮询周期；SF 路径沿用 `ResponsePollPeriod` 决定首拍，行为不变。两者各自只服务一条路径，不共用同一字段。

现有三个 SF 版本读取保留“串口写完起算、回显与 3D 轮询并行”的兼容路径；本文的新阶段和隔离规则针对多帧请求。SF 也必须修正未初始化截止参与判断的竞态，但不能未经回归将其强制改为等待回显再读 3D。多帧不得把现有 20 ms、1000 ms、5 s 默认值直接作为升级参数。

### 4.4 失败、取消与恢复

- 中途失败后不再提交剩余 CF。
- 取消或断线无法撤回已交给中间件的帧，结果应保留已发送进度。
- 停止计时和 3D 调度，处理在途写入，再释放事务状态。
- 按下表已选定的默认策略处理队列；恢复窗口作为阶段 0 的必确认项，不留到编码时再三选一。
- 默认不自动重试，避免重复执行设备命令。
- 成功、失败、取消、断线只允许产生一个最终结果。

#### 4.4.1 默认失败与队列恢复策略

| 结果/发生位置 | 本笔处理 | 后续排队与应用通信 |
|---|---|---|
| 多帧发送阶段失败，包括写入、回显、发送预算、帧间隔失败 | 停止剩余 CF，记录进度并统一收尾 | 中止整批，清空后续排队；在途写入收尾后退出诊断独占并恢复应用通信。未发出 3D、无待归属响应，不关闭跨事务门禁 |
| ProtocolAttributionError，不论发送或响应阶段 | 本笔失败，停止全部诊断调度 | 同上：清空后续队列，关闭跨事务门禁；收尾后恢复应用通信 |
| 普通 ResponseMismatch（含未解析的 `7F` 负响应） | 保留本笔 ResponseMismatch，完成收尾 | 不关闭门禁，继续 FIFO；负响应解析不在本阶段范围，但不得据此判定归属异常（§4.4.2） |
| ResponseDeadlineExceeded（多帧）或原 SF DeadlineExceeded | 保留本笔实际超时原因并清理响应状态 | 清空后续队列，但**不关闭**跨事务门禁；失败后可直接提交新请求（§4.4.2） |
| InvalidRequest、入队前已取消、排队期间取消 | 零发送结束该请求 | 不清空其他请求，不打断正在运行的请求 |
| 多帧已进入发送尝试后的调用者取消 | 返回 Cancelled，保留已发送/未知进度 | 按中止整批策略清空后续请求并收尾，避免从机半条请求后立即开始下一条 |
| 请求已发完、响应阶段取消 | 取消本笔并清理读取上下文 | 默认中止整批并关闭跨事务门禁，避免残留回复误归属下一笔 |
| Disconnected / Shutdown | 使用既有失败原因，停止调度 | 清空队列；断线/释放时不得强行恢复发送，重连仍只恢复应用通信 |

被整批清空的排队请求分别返回新增 `QueueAborted`，Progress 表示零次写入；不能伪装为它们自己的写入失败、调用者取消或断线。触发清空的本笔保留实际原因。队列清空与“正在收尾/恢复”状态必须原子发布，收尾期间新提交的请求返回 `QueueAborted`；门禁已经关闭后新提交的请求返回 `DiagnosticGateClosed`（§4.9.2），二者不得混用。任何新请求都不得绕过恢复边界；恢复完成且 §4.4.2 的跨事务门禁已解除后才重新接纳诊断。恢复应用通信不等于已解除诊断归属门禁。

默认策略明确选择“清空后续队列并恢复应用通信”，不把“设备已恢复”作为这一动作的结论。阶段 0 必须确认是否需要 `RecoveryWindow`、从何事件起算、应用帧是否可以立即恢复，以及何时允许新诊断。若需要等待，应将有界窗口放在恢复应用/接纳新诊断之前，并使用同源 TimeProvider；若设备明确不允许默认的立即恢复，必须先修订契约并阻塞不兼容方案，不能默认为零等待已获设备证明。

当前代码一笔失败后仍可能继续下一笔；上述中止整批行为需要实际修改 ProcessQueueAsync 和收尾/入队门禁，不能只在结果类型中增加原因。

#### 4.4.2 跨事务迟到响应：本版选择保守失败

原诊断架构将跨业务迟到包隔离列为未完成项，本计划明确承接该限制，不把本笔内回显过滤视为跨笔隔离已实现。

A 事务结束时，旧响应可能仍在中间件、串口缓冲、解析器缓存或已生成但尚未分发的候选中。B 开始读取后到达的 A 响应可能具有相同 NAD、DID 和完整正响应前缀；这些条件不能证明它属于 B。特别是无事务标识的完整旧 SF/FF，可能直接使 B 误报成功。

门禁触发范围（本版收窄，第六轮再次收窄）：

- 只在**确有证据表明旧回复可能仍在途**时关闭门禁：`ProtocolAttributionError`、响应阶段取消，以及已发出请求但未收齐响应时断线。
- **单纯超时不关闭门禁**（`ResponseDeadlineExceeded`、SF 的 `DeadlineExceeded`）。理由：超时意味着设备在窗口内根本没有应答，迟到响应本就极少存在；而一旦关锁，当前没有界面入口解除，只能重启应用，代价远大于它挡下的残余风险。超时仍按 §4.4.1 清空同批排队，但不阻断后续新请求。
- 前一笔**收到完整响应但前缀不符**不关闭门禁。此时本笔是唯一在途请求，没有其他事务能与它竞争归属，收到的只能是它自己的应答；这属于“设备拒绝”，不是“来路不明”，按 `ResponseMismatch` 报告后继续 FIFO。
- `7F` 负响应属于上一条：本阶段不解析负响应（§1.3），但也不得把它判成归属异常。负响应的结构化处理与验收留到升级业务阶段。
- 前一笔正常成功不关闭门禁。同 DID 连续事务仍受下文第 5 条“需要可验证归属保证”的声明约束，但不额外锁止。

已知残余风险（有意接受）：超时后立即重试时，若上一笔的响应恰好在本笔响应窗口内到达，且 NAD 与 DID 相同，仍可能被本笔认领为成功。当前业务只读版本号，最坏结果是显示错误版本；进入升级业务前必须先取得可验证的归属保证，届时需重新评估是否恢复超时锁止。

本版选择“保守失败”而不是声称固定静默窗口能完全解决：

1. 触发门禁的事务保持原失败原因，不因进入门禁改写为归属异常。
2. 门禁关闭后，已在队列中的请求清空为 `QueueAborted`，零次写入；此后新提交的请求返回 `DiagnosticGateClosed`，不发送新 3C/3D。可按 §4.4.1 恢复应用通信，但诊断准入保持关闭。
3. 不因“暂时没收到数据”、只清一次缓存、普通串口重连或换了软件事务代次就自动解除门禁。门禁只有在已确认的恢复过程完成后解除，例如具备标识的中间件排空确认，或协议明确保证设备与中间件旧回复已失效的复位流程；阶段 0 定义具体契约及其执行落点，未定义则不实现自动解除。
4. 若采用有界迟到时间契约，应明确覆盖中间件、物理串口及软件排队的最大寿命，并在停止旧读取、等待约定窗口后同步处理解析器残留和在途分发，再开启新事务。窗口不能凭经验指定，也不能靠每次收包无限续期。该契约可验证后，上述触发条件才可放宽。
5. 跨事务恢复同样适用于其他已发送后异常结束路径。正常成功后的连续事务也必须有中间件顺序/不重复或其他可验证归属保证；缺少保证时不能宣称任意同 DID 连续事务可靠。

解除途径（本阶段最小实现）：

- `DiagnosticTransactionService` 暴露只读 `IsDiagnosticBlocked` 与显式 `ResetDiagnosticGate()`。本阶段不接界面、不自动调用，供后续升级业务或人工确认设备已复位后使用。
- 未调用复位时，重启应用是唯一确定的解除方式；串口重连不解除。该后果必须写入交付说明，不能留给使用者猜测。
- 门禁关闭期间的结果必须与“排队被取消”可区分：使用 `DiagnosticGateClosed`，`FailureText` 显示“诊断已锁止，需复位或重启”，不得复用 `QueueAborted` 的取消文案。

软件事务代次只能隔离旧任务、旧回调和已标记的候选；当前无帧来源标识的原始字节若在 B 活动期间才到达，无法凭软件代次追溯到 A。§4.5 判定表第一行的“旧代次”仅适用于能被可靠标记的事件，不是原始线上包自带的事务身份。

因此“同 DID 迟到回复可能误成功”的场景应验收为：无可靠隔离契约时 B 明确保守失败且不发包，不能先接收旧响应再猜测归属。实现中不得以测试只注入可区分的不同 DID 来掩盖这个边界。

### 4.5 诊断候选判定表与回显隔离

3C 回显与 3D 响应均为 8 字节 PDU＋经典校验，NAD 也可能相同。因此不能使用“不是当前预期回显就投入 TP”的二分逻辑。

候选在入口保留原始日志后，按下表有序判定；“丢弃”仅指不交付业务/TP，不删除报文日志。先检查事务/连接代次、阶段截止和校验有效性。

| 阶段 | 候选条件 | 动作 | 是否进入响应 TP |
|---|---|---|---|
| 无活动事务、已结束或旧代次 | 任意候选 | 只记录，不认领 | 否 |
| 任意活动阶段 | 校验失败或无法形成有效候选 | 保留错误/未知日志，由原有解析恢复机制处理 | 否 |
| SendingRequest | 匹配当前已登记且已进入发送尝试的分片回显，并在有效截止内 | 记录一次确认，结合写入完成状态推进；不得因回显提前到达而漏记 | 否 |
| SendingRequest | 匹配已发送旧分片，含重复或迟到回显 | 标记旧回显，不重复推进或刷新当前截止 | 否 |
| SendingRequest | 其余校验通过的候选，包括同 NAD 的 SF/FF/CF | 标记发送期未认领候选并丢弃，不建立响应重组 | 否 |
| EchoDrain | 任意候选 | 匹配历史则记回显，否则记隔离期未认领候选；均丢弃 | 否 |
| WaitingResponse | 在容忍窗口内，匹配任一已发送分片原始回显 | 标记迟到/重复回显并丢弃，不刷新窗口或 N_Cr | 否 |
| WaitingResponse | 匹配历史但已超出承诺的回显容忍窗口 | 归属不明，记录并终止本笔为协议归属异常，不直接投入 TP | 否 |
| WaitingResponse | 不匹配历史、校验有效，且在本笔有效响应读取上下文内 | 由 TP 检查 NAD、PCI、长度和序号；错误 NAD 仍忽略 | 是 |
| WaitingResponse | 尚无有效响应读取上下文 | 只记录未认领候选 | 否 |

窗口定义：

- `EchoDrain` 是停止新 3C、尚未提交 3D 的固定隔离时间段，不是等待总线持续无数据后重计的无限静默等待。
- `EchoDrainDuration`、`EchoToleranceAfterLastComplete` 必须为明确配置，后者不小于前者；二者取值依据中间件最大反馈时延，不能凭空指定。
- `EchoFilterEnd = t_last_complete + EchoToleranceAfterLastComplete`，历史回显表保留到本笔结束；新候选不得延长窗口。
- 隔离结束时若解析器仍有不完整候选，不能直接带入响应阶段；必须通过明确的解析器边界接口处理并保留原始日志。清理共享缓存必须与接收处理同步，不能静默丢失数据或假装旧字节属于新阶段。
- 开始首个 3D 前建立“本笔已提交响应读取”的上下文；支持响应早于读取任务返回，但提交失败时不得认定成功。读上下文是约束条件，不是无标识回包归属的绝对证明。

不可判别边界与实施准入：

合法响应 CF 可能与某个旧请求 CF 字节完全相同。上述过滤会保守丢弃这种候选，因此仅靠字节匹配和固定窗口，不能声称能无歧义处理任意二进制请求/响应。同样，序号回绕后的相同请求分片会使旧回显与当前回显难以区分。

实施前必须获得至少一种可验证的归属依据：例如中间件提供帧来源/命令标识，或保证全部请求回显排空后才返回对应 3D 数据并给出可验证的最大迟到界限。若现有接口无法给出保证，只能限定已证明无冲突的业务范围并明确模糊候选导致失败，不能将本方案验收为任意消息均可靠。固定隔离窗口本身不构成该保证。

### 4.6 发送期间的 3D 与提前 NRC：明确选择

本版多帧选择方案 A：`SendingRequest` 与 `EchoDrain` 均不发送 3D。按当前接口与调度模式，从机只有获得 3D 读取机会才返回响应，因此本版无法提前读取 Bootloader 的拒绝结果。

接受的代价：如果设备在 FF 后已拒绝请求，上位机仍可能发送剩余全部 CF，直到请求发送完成后才读取 NRC，甚至因为设备后续行为只得到超时。不能宣称实现了提前 NRC 检测或提前中止。

上线前须确认设备在提前拒绝后对剩余 CF 的行为、NRC 保留时间及重组恢复规则。若设备要求及时读取 NRC，或后续 CF 会覆盖拒绝结果、使设备状态异常，则方案 A 不适用，应阻塞联调准入并改为方案 B。

方案 B 为独立协议变更：在分片间隙穿插受控 3D，明确读取频率、占用时间、最大 CF 间隔、回显/响应归属、NRC 解析和发送中止规则，并重做发送预算。不得同时声称“发送期间完全不发 3D”和“能够读取提前 NRC”，也不得在实现中隐式混用两种方案。

### 4.7 响应 TP 的启用与阶段切换

多帧路径不得沿用 RunTransactionAsync 中发送前 BeginReceive 的时机。

1. 进入 SendingRequest 前 Reset 清理上一笔 TP，但协调层明确禁用 TP 投递；现有 Reset 会回到 WaitingFirstFrame，不等于真正的“不接收”。可由协调层阶段门禁实现，无须假定 Reset 自带停用语义。
2. SendingRequest 与 EchoDrain 均不调用 ProcessPdu 或响应 N_Cr 检查；候选严格按 §4.5 处理。
3. 全部请求分片写入并确认后，确定 t_last_complete、ResponseDeadline，进入固定 EchoDrain。
4. 隔离结束且响应截止未到，处理解析器残留边界，再对当前 NAD 执行 Reset＋BeginReceive。
5. 原子发布 WaitingResponse 状态和有效计时，随后按首次读取约束提交 3D；不可先发 3D 再登记接收状态。
6. WaitingResponse 才允许候选进入 TP，才检查响应 N_Cr。失败、取消、断线时关闭门禁、失效回调、Reset 并统一收尾。

状态发布与跨层调用须按现有锁序设计；原子切换不代表在锁内执行串口 I/O 或等待异步任务。实施时以代次与阶段二次校验消除检查和执行间隙。

### 4.9 失败原因、进度与用户文案的明确契约

#### 4.9.1 结果进度

在 `Diagnostics.cs` 增加不可变 `DiagnosticProgress`，并给 `DiagnosticResult` 增加 Progress 属性；成功、失败工厂都能携带最终快照。建议字段如下，索引统一从 0 开始：

| 字段 | 定义 |
|---|---|
| TotalPduCount | 校验/分包成功后预计 PDU 数；尚未确定时为可空值 |
| WriteAttemptCount | 已调用发送出口的 PDU 数，含当前失败或未知完成状态的一片 |
| SerialWriteCompletedCount | 已取得成功写入回执的 PDU 数，不等于已上总线或设备已接收 |
| EchoConfirmedCount | 已确认有效回显的 PDU 数，重复回显不累计 |
| UdsBytesWriteCompleted | 成功写入分片内的有效 UDS 字节之和，排除 NAD、PCI、填充和校验 |
| CurrentPduIndex | 结束时当前操作分片索引；尚未开始或无当前分片时为 null |
| FailedPhase | DiagnosticPhase?；取值和赋值规则见下表，成功时为 null |
| InFlightWriteAtCompletion | 最终结果确定时是否仍有未取得明确结果的写入，防止把未知误报为未发送 |

回显可能早于写入任务完成，因此不能假定瞬时 EchoConfirmedCount 始终小于 SerialWriteCompletedCount。两者均不得超过 WriteAttemptCount。最终发布使用冻结快照，不让后台迟到完成修改已交付结果；未知的在途发送明确标注，后续排查记录独立保留。

排队时取消/断线可以返回“零次写入”的进度；成功时三项计数应与总片数一致（本版逐帧确认策略）。参数错误在发送前返回失败，未确定分片数保持 null。

在 `Diagnostics.cs` 明确定义 `DiagnosticPhase` 枚举：

| 枚举值 | 含义/FailedPhase 赋值示例 |
|---|---|
| Validating | 入队前校验；InvalidRequest、预取消、恢复门禁拒绝时使用 |
| Queued | 已入队尚未执行；排队取消、断线或被整批清空时使用 |
| EnteringDiagnostic | 已出队，正在获取独占且尚未发送；此期间失败使用 |
| SendingRequest | 请求写入、逐片确认或帧间隔等待；包括 SF 请求写入阶段 |
| EchoDrain | 多帧发送完成后的固定回显隔离 |
| WaitingResponse | 响应读取与重组；SF 并行等待有效回显和响应也归此阶段 |
| Recovery | 本笔仍待完成时执行必要的失败恢复/跨事务隔离；只在此处新产生终止原因时使用 |
| Finalizing | 本笔仍待完成时处理收尾；只在收尾本身新产生终止原因时使用 |

FailedPhase 在终止原因首次胜出时取快照，不能因为随后进入 Recovery/Finalizing 就覆盖原失败发生阶段。成功结果为 null；已发布结果不因后台收尾变化而变更。QueueAborted 的排队等待者使用 Queued，未入队即被恢复门禁拒绝者使用 Validating。实现状态、结果字段和测试断言共用该枚举，不使用自由文本阶段名。

#### 4.9.2 失败枚举

保留现有枚举值及其编号，新增值追加，避免改变旧数据解释。新增/复用规则：

| Reason | 使用范围 |
|---|---|
| InvalidRequest | 长度、必填多帧选项或参数组合非法，发送前拒绝 |
| RequestWriteFailed（已有） | 实际串口写入异常 |
| RequestWriteTimeout（新增） | 单片写入等待超时，可能存在在途未知状态 |
| EchoTimeout（已有） | 当前分片回显截止到期，Progress 标识索引 |
| SendDeadlineExceeded（新增） | 发送阶段预算耗尽 |
| InterFrameDeadlineExceeded（新增） | 不能满足最大相邻分片间隔 |
| ResponseDeadlineExceeded（新增） | 多帧请求的响应预算耗尽，包含隔离期 |
| ProtocolAttributionError（新增） | 已确认的归属规则被破坏，或遇到不能安全交付 TP 的模糊候选 |
| Cancelled（新增） | 调用者取消 |
| QueueAborted（新增） | 前序事务中止整批而清空队列，或处于失败收尾期；本请求未发送 |
| DiagnosticGateClosed（新增） | 跨事务门禁已关闭、诊断准入暂停；本请求未发送，需显式复位或重启（§4.4.2） |
| ResponseMismatch / Disconnected / Shutdown（已有） | 继续沿用原语义，附进度 |
| DeadlineExceeded（已有） | 保留原 SF 5 s 截止语义，多帧不再复用它隐藏失败阶段 |

N_Cr 和 TP 放弃仍按既有策略记录 TpAbandonReason，不能在本次擅自改为新的立即结束策略。尚未实现 NRC 解析，本轮不得新增“已识别具体 NRC”的虚假结果。

`DeviceVersionResult.FailureText` 必须对所有可达失败值作显式映射；新增值不得无声落入默认“读取失败”。发送超时、响应超时、协议归属异常、取消应使用各自准确文案。SF 当前通常不可达的多帧原因也应明确映射，并由临时测试遍历所有失败枚举（排除 None）核查。未知未来枚举可保留兜底，但应显示原因标识并记录，不能掩盖已知值遗漏。

进度本轮供结果、日志和临时测试使用，不要求新增 UI 进度条。现有版本业务返回值继续保留 FailureReason；多帧调用方直接接收完整 DiagnosticResult。

### 4.10 参数归属：SF 与多帧分开

原 `DiagnosticTiming` 保持五个现有 SF 参数及原行为，不为单帧调用者塞入多帧专属参数。建议新增 `DiagnosticMultiFrameOptions.cs`，类型结构固定如下：

```text
DiagnosticRequest
  Timing: DiagnosticTiming                         // 原 SF 路径
  MultiFrameOptions: DiagnosticMultiFrameOptions?   // 长请求显式提供

DiagnosticMultiFrameOptions
  MaxRequestLength
  Send: DiagnosticSendTiming
  Response: DiagnosticResponseTiming
```

| 参数 | 明确归属 | 说明 |
|---|---|---|
| MaxRequestLength | DiagnosticMultiFrameOptions | 业务/设备接收上限，不能超过编码上限 |
| WriteBudget | DiagnosticSendTiming | 每片写入等待上限 |
| EchoBudget | DiagnosticSendTiming | 每片回显等待上限 |
| MinimumInterFrameGap | DiagnosticSendTiming | 最小发送间隔，与最大上限区分 |
| InterFrameGapBudget | DiagnosticSendTiming | 最大允许相邻间隔；锚点由设备契约明确，与最小间隔校验 |
| SchedulingMargin | DiagnosticSendTiming | 发送预算中有界的调度余量 |
| SendBudget(N) | 协调层纯计算方法 CalculateSendBudget(N, Send) | 派生值，不是要求调用者配置的第九个字段，使用 §4.3 模型并检查溢出 |
| SendBudgetOverride（可选） | DiagnosticSendTiming | 如提供显式总发送上限，须通过最坏预算可行性校验 |
| EchoDrainDuration | DiagnosticSendTiming | 固定隔离长度 |
| EchoToleranceAfterLastComplete | DiagnosticSendTiming | 历史回显容忍窗口，不小于隔离长度 |
| ResponseBudget | DiagnosticResponseTiming | 从 t_last_complete 起算的响应总预算 |
| FirstResponsePollDelay / ResponsePollPeriod | DiagnosticResponseTiming | 多帧响应首读延迟和周期，分别生效 |
| ConsecutiveFrameTimeout | DiagnosticResponseTiming | 响应 TP 的 N_Cr |

入队前校验：L≤6 走原 SF Timing；L>6 必须提供完整 MultiFrameOptions，缺失即 InvalidRequest，不静默填入旧 5 s/20 ms。原版本读取继续只提供 Timing，不受新多帧必填项影响。

硬性配置隔离：**L>6 时 DiagnosticRequest.Timing 完全不参与参数校验、计时、截止、首读延迟、轮询周期、回显等待、响应 N_Cr 或任何运行期回退。** 即使该属性保留 DiagnosticTiming.Default，或调用方显式设置为极小值，多帧也只读取 MultiFrameOptions。任何多帧路径读取 request.Timing 来决定上述行为均视为缺陷。

为防止隐式回退，入队时按长度选择 SF/多帧执行配置并生成各自不可变快照，运行期与定时器回调使用该已选配置，不再从原始 request 混取两套参数。多帧执行上下文不携带可被误读的 SF Timing；相应校验也仅检查选中路径的参数。

新选项创建不可变快照，并校验长度、正值/允许零值、最小/最大间隔、窗口大小关系、预算覆盖及时间换算溢出。具体数值仍待协议确认，类型归属不再待定。

### 4.11 多帧请求发起入口与范围

生产接口计划固定为：

```csharp
Task<DiagnosticResult> ExecuteAsync(
    DiagnosticRequest request,
    CancellationToken cancellationToken = default);
```

保留原调用兼容性，现有不传 token 的版本读取无需改变调用形式；CancellationToken 不塞入请求配置 record。

取消契约：

- 入队前已取消：立即返回失败结果 Cancelled、零次写入，不入队，不获取独占。
- 排队期间：提交时即登记 token 回调，取消时立即完成该排队任务为 Cancelled；从 FIFO 移除或标记失效并在出队跳过，不必等前序请求完成，不取消前序请求。
- 从出队、获取独占到首片发送前继续检查取消；尚未发送时按零发送取消，正确收尾且不误清其他请求。
- 运行期间 token 传递到调度器/通道现有发送方法，并覆盖新增的分片延时、回显等待、隔离及响应等待；取消不以收到下一个串口事件为前提。
- 本 API 统一返回 DiagnosticResult.Failed(Cancelled)，不混用被取消 Task 和失败结果两套对外语义；底层 OperationCanceledException 在协调层转换，真正断线/写入异常不得一律伪装为取消。
- 回调、正常完成、超时和断线通过同一个完成门禁竞争，最终结果唯一；结束后释放 token 注册。不能在锁内 Dispose 一个可能正等待同一锁的取消注册，也不能把底层请求取消视为在途物理发送已撤回。
- 是否清空其他请求按 §4.4.1 的阶段和发送进度执行。

阶段 3 的完整链路由仓库外临时测试工程直接调用上述 ExecuteAsync 发起：传入大于 6 字节的完整 UDS 请求、明确的 MultiFrameOptions、预期响应规则和可控 token，由串口替身注入回显和响应。

不新增升级按钮、命令行开关、隐藏菜单或产品内调试入口，不把长请求塞入 `DeviceInformationService.ReadVersionAsync`。正式多帧业务调用方由后续升级业务阶段添加；本阶段无界面入口不妨碍验证真实服务调用链。实机测试如需触发，同样由外部临时验证程序组装真实串口服务并调用该接口，完成后清理，不在产品中保留测试命令。

## 5. 潜在风险与边界情况

| 风险或边界 | 处理与验证重点 |
|---|---|
| 快速回显早于计时初始化 | 当前 active 先登记、截止时间后赋值，存在零值截止参与判断的窗口；先建立复现测试，再通过明确阶段及计时有效标志修正 |
| 3C CF 回显进入响应重组 | 强制实施 §4.5 判定表，发送期关闭 TP，旧回显不得透传 |
| 首帧起算 5 s 掐断长请求 | 强制分离 SendDeadline 与 ResponseDeadline，定时器和接收入口按阶段检查 |
| 发送前 BeginReceive 导致污染 | 强制按 §4.7 后移启用，Reset 不等于停用 |
| 不发 3D 却期待提前 NRC | 本版明确接受不能提前读取的代价，设备不兼容则切换方案并重新定案 |
| 序号回绕后出现相同分片内容 | 仅按字节匹配无法彻底排除迟到重复回显，需要中间件顺序保证或明确恢复约束 |
| 连续发送导致中间件积压 | 有界发送、明确回压，用总线抓包确认节奏 |
| 定时器延迟或系统高负载 | 使用单调时钟，检查最大允许间隔，不集中补发 |
| 最后回显与响应交错 | 多帧按固定隔离及判定表处理；SF 保留现有并行行为并分别测试 |
| 部分发送后断线重连 | 旧任务、旧计时器不得继续发送或结束新事务，不自动重放 |
| 9 字节候选粘包、拆包、噪声 | 验证共享解析器持续处理及 50 ms 不完整帧超时边界 |
| 排队期间数组被修改 | 入队前复制请求及响应规则 |
| 队列清空时新请求加入 | 不得意外恢复应用发送或误清新状态 |
| 锁和异步回调形成竞争 | 保持明确锁序，不在锁内执行跨层回调或等待异步任务，验证同步完成和异步完成两条路径 |
| 升级请求收到负响应 | 本阶段不解析：按 `ResponseMismatch` 报告，且不触发跨事务门禁；正式升级前实现负响应策略并单独验收（§4.4.2） |

其中回显初始化竞态为源码检查发现的风险窗口，尚未通过本次运行测试确认；应在基线阶段验证，而不是视为已完成修复。

## 7. 验证计划

### 7.1 分包测试

### 7.2 事务与故障注入测试

- SF 请求→SF 响应、SF 请求→多帧响应。
- 多帧请求→SF 响应、多帧请求→多帧响应。
- 回显同步到达、延迟、缺失、重复、损坏。
- 最后回显与响应以不同顺序交错到达。
- 第一个、中间、最后一个分片写入失败或断线。
- 排队、分片间隔、等待回显、等待响应期间取消。
- 发送忙、计时延迟、队列交接、连续提交诊断。
- 清理后余下 CF 不再发送，旧计时回调不影响新事务。
- 单笔最终结果唯一，队列推进唯一，无永久占用或死锁。

### 7.3 原功能回归

- 三个版本读取的请求字节和结果解析。
- 现有 3D FF/CF 重组、长度和序号检查、N_Cr。
- 应用 0x15/0x33 通信、单帧边界暂停、队列清空后恢复。

2. 同时保留串口 TX/RX 记录和 LIN 总线抓包。

### 7.5 强制验收用例矩阵

覆盖历次修订的全部强制约束：分包与时间模型、归属与隔离、失败与恢复、配置隔离。全部用例均在仓库外临时工程中以虚拟时间执行（§7.6）。

| 用例 | 必须观察到的结果 |
|---|---|
| 4095 字节、683 帧，仿真按 20 ms 相邻间隔运行超过 13 s | 在 SendBudget 有效时不因旧 5 s 响应上限失败，响应预算从最后完成事件起算 |
| 发送中超过 SendDeadline、回显超时或间隔上限 | 停止后续分片，返回对应发送失败；不启用响应 TP |
| 最后写入与回显以两种顺序到达 | t_last_complete 都取两者满足条件的时刻，截止只初始化一次 |
| 隔离窗口消耗完响应预算 | 不发送新 3D，返回响应截止；不得重新起算预算 |
| 发送阶段注入同 NAD 的杂散 FF、CF、SF | 均记录且不投入 TP，接收缓冲和 N_Cr 不被启动 |
| 已推进到 N+1 时收到分片 N 的重复回显 | 不推进当前分片，不刷新截止，不调用 ProcessPdu |
| 响应 FF 后插入旧请求 CF 回显 | 容忍窗口内按历史回显丢弃，响应预期序号不变；随后正确响应 CF 能继续重组 |
| 超出回显窗口后再次收到历史匹配候选 | 按归属异常处理，不作为响应投入 TP |
| 合法响应 CF 与历史请求 CF 完全相同 | 验证归属契约能区分，或明确保守失败；禁止将误丢包描述成“完全支持” |
| 隔离期间持续出现重复回显 | 不延长 DrainEnd、EchoFilterEnd 或 ResponseDeadline |
| 发送期已有残缺候选，跨隔离结束才补齐 | 依据解析边界契约处理并保留日志，不把旧数据静默转为新响应 |
| FF 后模拟设备提前拒绝 | 方案 A 确认发送阶段没有 3D，也不宣称提前获知 NRC；发送结束后结果符合设备约定 |
| 首个 3D 响应早于串口写任务返回 | TP 和读取上下文已登记，不漏收；提交失败仍不得误报成功 |
| 每次阶段切换时断线、取消或旧定时器触发 | 不重启 TP、不误结束下一笔、不重放余下 CF |
| 长请求使用合法 MultiFrameOptions，但 Timing 的五个值均设为 1 ms，发送/响应持续明显超过 1 ms | 正常按 MultiFrameOptions 完成；与保留 Timing 默认值时的发送序列及计时行为一致，不出现 1 ms 或旧 5 s 截断 |
| 长请求的 Timing 不满足 SF 校验约束，但 MultiFrameOptions 合法 | 不因未选中的 SF 配置而拒绝，多帧校验不读取 Timing |
| A 超时后，同 NAD/同 DID 的 B 已排队 | B 得到 QueueAborted、零发送；A 的超时**不关闭**门禁，随后新提交的 C 被接纳并正常发送 |
| A 归属异常后，同 NAD/同 DID 的 B 已排队 | B 得到 QueueAborted、零发送；门禁关闭，新提交返回 `DiagnosticGateClosed`；注入旧包不得使任何请求成功 |
| SF 版本读取收到 `7F 22 xx` 负响应 | 返回 `ResponseMismatch`；不关闭跨事务门禁；后续诊断正常发送，不得出现 `DiagnosticGateClosed` |
| 门禁关闭后新提交诊断 | 返回 `DiagnosticGateClosed`、零发送；串口重连不解除；调用 `ResetDiagnosticGate()` 或重启后恢复 |
| 门禁关闭时队列中仍有等待者 | 排队者返回 `QueueAborted`，与 `DiagnosticGateClosed` 可区分，两者 Progress 均为零写入 |
| 已确认恢复契约后，旧回复跨越恢复边界、残留候选延迟分发 | 验证排空/失效证明、缓存与分发同步；若契约被破坏则归属异常并关闭门禁，不能误认 B 成功 |

以上验证必须分别覆盖接收硬截止和 InspectTimerCallback，不能仅证明计时器路径正确。当前只制定用例，本轮未运行这些测试。

### 7.6 测试落点、结果契约和交付清理验收

- 使用同一 FakeTimeProvider 覆盖写入回执、接收时间、TP N_Cr、调度与检查定时器；验证不存在混用 Stopwatch 频率或真实 Timer 导致的时间域错误。
- 不使用真实等待 13 s 代替长请求的可推进时钟测试；另外独立执行系统计时和实机时序验证。
- SF 无 MultiFrameOptions 仍可执行；长请求缺选项、窗口/预算非法时在零发送状态失败。
- 每个失败路径按 DiagnosticPhase 枚举核对 FailedPhase，并核对 Reason、分片索引、计数及有效 UDS 字节；收尾不能覆盖原失败阶段，在途未知状态不能写成“设备已接收”。
- 遍历失败枚举验证 FailureText 显式映射，不以默认“读取失败”掩盖遗漏。
- 测试工程直接 ExecuteAsync 发起长请求；原三个版本读取不被改成测试入口，产品中不新增按钮或隐藏开关。
- 普通 net10.0 白名单工程独立编译通过，无 CommunicationLogService/Dispatcher/DispatcherTimer 意外依赖；备选 WPF 宿主必须使用匹配目标框架，不能靠遗漏类型或修改待测算法绕过编译。
- 前序事务阻塞时取消后续排队请求：后者立即返回 Cancelled、零发送，前者继续；覆盖预取消、获取独占时取消和运行期四类等待点。
- 验证取消注册生命周期、完成竞争及未传 token 的旧调用兼容性；结果不得混用失败结果与 TaskCanceledException。
- 发送失败或归属异常后，已在队列的请求得到 `QueueAborted`、零发送；归属异常、响应阶段取消、带在途请求断线后门禁关闭，新提交返回 `DiagnosticGateClosed`；单纯超时不关门禁，可直接重试。停止余下 CF，在途收尾后按约定恢复应用。`ResponseMismatch`（含 `7F`）不关门禁，继续 FIFO。
- 清空队列期间新请求不可越过恢复门禁；断线时不恢复发送；若阶段 0 确认恢复窗口，使用虚拟时间验证窗口前后应用及新诊断准入边界。
- 测试完成或中止后，确认外部临时目录删除；仓库内无测试工程、替身、测试依赖、测试脚本及测试产物，WpfApp1.slnx 仍只挂原产品项目。
- 记录最终验证所对应的源码状态，清理不得回退已验证的 TimeProvider 产品改造；正式文档保留验证结论而非测试代码。

### 10.2 实施期新增的设计细节

- SF 路径发送前先登记临时截止，消除“回显早于写入返回时 0 截止直接判超时”的竞态；写入返回后再按 t0 重算。
- 新增事务级 `Lifecycle` 信号，使发送循环在定时器/接收路径已判定失败后立即退出，不再空等写入或回显预算。
- 隔离结束后先 `EndReceive` 语义的 `BeginReceive`，再发布 `WaitingResponse`，缩小“阶段已切换但 TP 尚未就绪”的窗口。
- 取消注册在队列循环或析构路径统一释放；不在 `stateLock` 内释放可能等待同一锁的注册。
- 审查修复追加（详见《3C多帧实现审查与修复方案.md》§7.4）：发送阶段先匹配当前待确认片；响应认领绑定真实 3D 写入回执，首次读取在途时暂存候选、成功回执后按原接收时间重放；事务结果冻结后立即完成调用者等待，发送出口排空与结果发布分离；等待独占期间可取消并及时撤销无主申请。
