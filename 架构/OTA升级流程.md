## 第一步：诊断在线探测

### 1.1 目标与通过条件

进入 OTA 后，要求连续三次探测成功，才允许执行下一升级步骤。

- 单次成功：收到有效中间件 3C 回显，且收到本次设备正响应 `7E 00`。
- 第一次探测失败：累计失败次数加一，连续成功次数清零，等待规定间隔后重新探测。
- 本次在线确认阶段累计第二次失败：退出本次 OTA，不执行后续升级步骤。
- 两次失败不要求连续发生；成功不清除累计失败次数。
- 在线探测通过只代表设备能够进行诊断应答，不代表已进入编程会话、已解锁或已允许下载。

### 1.2 点击 OTA 后的应用通信切换

沿用执行器调试界面触发诊断时的应用暂停与回复收尾策略，由统一调度器执行：

1. 点击开始 OTA，立即禁止启动下一条应用帧，包括 `0x15/0x33/0x34`。
2. 已开始的当前应用串口写入正常完成，不打断，不等待完成整拍。
3. 沿用应用待回复登记：从触发暂停时刻 `t_req` 起，最多等待 100 ms。
4. 无待回复登记，或登记提前全部清空：当前写入完成后立即允许首个诊断请求。
5. 到 `t_req + 100 ms` 仍有登记：清除全部登记；当前写入已完成则放行。
6. 当前写入跨过 100 ms 截止：仍等它写完，写完后直接放行，不重新追加 100 ms。
7. 等待期间 RX、组帧、校验、日志和分发保持运行。清除登记不等于清空接收缓存。

在线探测阶段的各笔事务、探测间隔、失败后的重新探测及后续升级步骤之间，持续持有 OTA 独占，不恢复应用帧，不插入其他诊断业务。

当前应用回复收尾机制已存在于 `LinBusScheduler`；覆盖整个 OTA 的独占生命周期已由 `DiagnosticTransactionService.BeginOtaExclusiveHold/EndOtaExclusiveHoldAsync` 实现。不能仅依赖现有“诊断队列清空即恢复应用帧”的行为。

### 1.3 固定报文与单次探测流程

本文所有字节均为十六进制，以下内容为上位机与中间件之间的串口数据。目标 NAD 固定为 `0x78`。

#### 1.3.1 发送 TesterPresent

```text
55 AA 55 3C 08 | 78 02 3E 00 FF FF FF FF | 47
```

- `55 AA`：中间件串口接口对 Break 的表示。
- `55`：Sync。
- `3C`：诊断请求 PID。
- `08`：写入标识。
- `78`：NAD。
- `02`：单帧有效 UDS 长度为 2 字节。
- `3E 00`：TesterPresent 请求。
- `FF FF FF FF`：PDU 填充。
- `47`：8 字节 PDU 的经典校验。

#### 1.3.2 接收并核对中间件回显

```text
78 02 3E 00 FF FF FF FF | 47
```

回显不带串口帧头。按请求 PDU 加校验逐字节核对；有效回显只证明本次中间件反馈通过，不单独判为设备在线。

#### 1.3.3 发送 3D，提供响应读取机会

```text
55 AA 55 7D 00
```

- `7D`：诊断响应 ID `0x3D` 对应的 PID。
- `00`：读取标识。
- 本请求无 DATA、无 Checksum。

用户随后确认：3D 发送时机与执行器调试界面的现有 SF 诊断一致。记 `t0` 为 3C 串口写入完成时刻，首次 3D 在 `t0 + 20 ms` 启动，与回显等待并行，不以有效回显先到为条件。无响应时继续按 20 ms 固定节拍轮询，直到本笔提前结束或达到截止；完整规则见第 1.8 节。

本节覆盖此前“先确认回显再启动 3D”的顺序描述。第 1.3.1～1.3.4 节的编号用于说明报文种类，不强制回显与设备响应的接收先后。

#### 1.3.4 接收设备正响应

```text
78 02 7E 00 FF FF FF FF | 07
```

检查 NAD、单帧长度、UDS 内容和经典校验：完整 UDS 消息应恰好为两字节 `7E 00`，不能只匹配前缀后接受额外 UDS 数据。

经典校验仅计算 8 字节 PDU：累加，超过 `FF` 时反复减 `FF`，最后取反。请求校验为 `47`，正响应校验为 `07`；帧头、PID 和 `08/00` 不参与校验。

#### 1.3.5 一笔事务的边界

```text
发送 3C → 串口写入完成，记 t0
               ├─ 独立等待并核对回显，截止 t0 + 1000 ms
               └─ t0 + 20 ms 起，每 20 ms 读取 3D，核对设备响应
                                      ↓
                   回显与响应均通过 → 成功；异常或截止 → 本次失败
```

前一笔完整结束后才允许下一笔探测，不连续发送三个 3C 后统一读取。重复回显或重复响应不能重复累计成功次数。

### 1.4 两次探测之间的间隔

- 间隔：固定 1 s。
- 起点：上一笔探测被判定成功或失败的时刻。
- 下一笔首个 3C 的提交时间不早于该时刻加 1 s，且仍须满足上一笔在途写入已排空等发送条件。
- 第一次失败后的下一笔同样等待 1 s。
- 达到连续三次成功时，直接进入下一升级步骤，不为已不存在的下一笔探测额外等待 1 s。
- 累计第二次失败时，直接进入退出收尾，不再安排下一笔探测。
- 1 s 是两笔探测之间的间隔，不是单次回显超时、响应超时或 3D 轮询周期。
- 间隔期间继续接收和记录数据，应用帧保持暂停。

### 1.5 计数和决策

进入本次在线确认阶段时初始化：

```text
consecutiveSuccessCount = 0
failureCount = 0
```

每笔只处理一次最终结果：

```text
本次成功：
    consecutiveSuccessCount += 1
    failureCount 保持不变
    连续成功达到 3 → 在线确认通过，进入下一升级步骤
    否则 → 等待 1 s，再探测

本次失败：
    failureCount += 1
    consecutiveSuccessCount = 0
    累计失败达到 2 → 退出本次 OTA
    否则 → 等待 1 s，重新争取连续三次成功
```

此规则不是“只发三次”，也不是“只重试一笔、成功即通过”；第一次失败后仍必须重新获得连续三次成功。按此计数，在线确认阶段最多执行六笔探测，不包含一笔事务内部可能进行的多次 3D 读取。

| 结果序列 | 决策 |
| --- | --- |
| 成功 → 成功 → 成功 | 通过 |
| 失败 → 成功 → 成功 → 成功 | 通过 |
| 成功 → 失败 → 成功 → 成功 → 成功 | 通过 |
| 成功 → 成功 → 失败 → 成功 → 成功 → 成功 | 通过，六笔探测 |
| 失败 → 失败 | 第二次失败时退出 |
| 失败 → 成功 → 成功 → 失败 | 累计第二次失败，退出 |

### 1.6 退出、交接与日志

#### 1.6.1 在线确认通过

- 停止本阶段新的 3D 调度，完成本笔事务清理与实际写入排空。
- 保持 OTA 独占，将执行权交给下一升级步骤。
- 不恢复应用帧，不把在线确认通过显示为升级完成。

#### 1.6.2 累计第二次探测失败

- 不再提交本阶段新的 3C/3D，不执行后续升级步骤。
- 清理本阶段等待、计时和接收上下文，等待已经开始的真实写入完成。
- 收尾后退出 OTA 独占；连接仍有效时按既有调度策略恢复应用通信。
- 断线时保持停止发送，不强行恢复应用通信，不自动重放本次 OTA。
- 应用暂停标志与诊断准入门禁分别处理，不因退出 OTA 或恢复应用而自动解除诊断门禁。

串口断开、应用退出等生命周期终止直接结束本次 OTA，不在断线或已释放状态下消耗剩余探测机会。

日志至少记录：当前探测序号、单次结果、连续成功次数、累计失败次数、失败原因和最终阶段结论；原始收发字节继续进入共享报文日志。

### 1.8 单次探测时序与剩余边界

#### 1.8.1 已确认：与执行器调试界面的 SF 诊断一致

用户明确确认回显超时、3D 发送时机、无响应时的轮询间隔及响应超时均沿用现有单帧诊断；对应 `DiagnosticTiming` 默认值及 `SendSingleFrameRequestAsync` 执行语义如下。

| 参数 / 行为 | 本阶段规则 |
| --- | --- |
| t0 | 本笔 3C 串口写入完成时刻，不是按钮点击、入队或收到回显时刻 |
| 回显等待截止 | `t0 + 1000 ms`；缺少有效回显则本次失败，不必等满 5 s |
| 首次 3D | `t0 + 20 ms`，不等待回显通过才启动 |
| 无响应时 | 继续轮询，后续节拍为 `t0 + n × 20 ms`，n ≥ 1 |
| 出口忙或错过节拍 | 沿用现有跳拍机制，不堆积、不集中补发 |
| 单次响应截止 | 初始为 `t0 + 5 s`；有效 NRC `78` 到达时按 §6.5 刷新，发送 3D、回显及无效数据不刷新 |
| 成功条件 | 有效回显与完整且匹配的 `7E 00` 响应均通过 |
| 响应先通过、回显尚未通过 | 保存响应、停止新的 3D，在原回显窗口内继续等待；回显到期仍未通过则失败 |
| 回显先通过、响应尚未到达 | 保持轮询，直到响应通过或本笔结束 |
| 提前结束 | 成功或失败即停止本笔新的 3D；实际在途写入按原机制排空 |

```text
t0             3C 串口写完，开始独立等待回显
t0 + 20 ms     首次 3D
t0 + 40 ms     后续 3D
t0 + 60 ms     后续 3D
……             未提前结束则持续轮询
t0 + 1000 ms   尚无有效回显 → 本次失败并停止新 3D
t0 + 5000 ms   回显已通过、响应仍未通过 → 本次失败并停止新 3D
```

应用回复收尾发生在首笔 3C 之前，不计入该笔 5 s。两笔探测之间的 1 s 从上一笔最终结果起算，与上述各个截止独立；前一笔收尾未完成时，下一笔仍须等发送资源可用。

#### 1.8.2 异常数据与迟到响应边界

校验错误不进入 TP，错误 NAD 由 TP 忽略，不将每一个无效候选单独计为一次探测失败；本笔最终结果失败时才更新失败计数。有效 `7F` 需原 SID 与本笔请求一致。非 `78` 负响应结束本笔并计失败；`78` 进入响应待定、刷新等待窗口并继续读取，不计为本次探测失败，也不增加连续成功次数，见 §6.5（已实现）。

两笔探测报文完全相同。1 s 间隔不能单独证明上一笔迟到响应已失效；需结合中间件和设备的最大反馈时延、顺序或排空保证，确认第一次失败后的重试不会把旧响应认作新成功。软件代次只能隔离旧任务，不能替无标识原始字节证明来源。

### 1.9 后续验证范围

- 三次连续成功、第一次失败后成功计数清零、累计第二次失败退出。
- 成功和第一次失败后，下一笔提交均至少间隔 1 s。
- 3C 写完后 20 ms 启动 3D，与回显等待并行；无响应时每 20 ms 轮询，忙则跳拍。

- 回显先到与响应先到均正确处理；响应先到时停新 3D，并在原回显窗口内判定结果。
- 探测间隔、事务交接及进入后续升级步骤时，无应用帧插入。
- 回显缺失、响应缺失、错误校验、错误 NAD、负响应、重复和迟到数据。
- 断线、取消或释放时结果唯一、停止新发送，已开始写入按真实完成收尾。
- 静态检查、仿真与构建结果分别记录；实际串口和 LIN 时序需实机抓包确认。

### 版本读取与解析

- 三个请求都是 SF，请求消息长 3 字节，PDU 中 `03` 为有效 UDS 长度，`FF` 为填充。
- 3C 回显按请求 PDU + 经典校验逐字节核对；每笔成功均须有效回显和完整业务响应验证通过。
- 响应可为 SF 或 FF/CF，不固定版本字符串长度，不固定 3D 读取次数，不直接复用其他版本样例的总长度。
- 校验、NAD、PCI、长度、CF 序号及 4 位回绕检查复用现有 TP；多帧响应的 N_Cr 为 1000 ms。
- 业务按各自 `62 + DID` 核对正响应前缀，再去掉前 3 字节，将剩余有效 UDS 字节按 ASCII 解释，并沿用现有 `TrimEnd()`。
- 当前业务层不额外要求字符串非空，不在本次文档中增加与现有实现不同的版本格式校验。

### 6.2 请求、回显与响应报文

以下示例使用默认 NAD `78`；更换 NAD 后必须重新计算校验。

```text
发送 3C：55 AA 55 3C 08 78 02 10 03 FF FF FF FF 72
接收回显：               78 02 10 03 FF FF FF FF 72
发送 3D：55 AA 55 7D 00

正响应示例（PDU + CS）：78 06 50 03 00 32 01 F4 06
负响应通式（PDU + CS）：78 03 7F 10 NRC FF FF FF CS
```

负响应示例：

```text
78 03 7F 10 22 FF FF FF D2 → 条件不满足
78 03 7F 10 78 FF FF FF 7C → 请求已接收，响应待定
```

`7F` 是负响应服务标识，`10` 是被拒绝或待处理的原请求服务号，后一个字节才是 NRC。不能把 NRC `78` 与 NAD `78` 混淆；也不能把 NRC `7E` 与 TesterPresent 正响应 SID `7E` 混淆。

### 6.3 正响应解析与成功条件

| 字段 | 示例 | 解释 |
| --- | --- | --- |
| NAD | `78` | 本次 OTA 目标地址 |
| SF PCI | `06` | 完整 UDS 消息为 6 字节 |
| 正响应 SID | `50` | `10` 服务对应的正响应 |
| 会话类型 | `03` | 扩展诊断会话 |
| P2Server_max 数据 | `00 32` | 当前忽略，不解析、不用于计时 |
| P2*Server_max 数据 | `01 F4` | 当前忽略，不解析、不用于计时 |
| CS | `06` | 此示例 8 字节 PDU 的经典校验 |

用户给出的 `78 06 50 03 00 32 01 F4` 是完整 8 字节 PDU，串口接收时还包括第九字节 CS。

按已确认格式校验完整 UDS 长度为 6 字节、前两字节为 `50 03`。后四字节作为未解释的响应数据接收，不要求等于 `00 32 01 F4`，不检查其数值范围，不提取为 P2/P2* 属性。它们仍属于完整 PDU，参与经典校验，不可在传输层截掉。

成功须有效 3C 回显与合法正响应同时满足。正响应先通过时仍沿用原回显等待规则；只有最终成功，才发布“已进入扩展诊断会话”并进入第七步，不额外保存解析后的会话时间参数。

本阶段不使用返回的会话时间数据改变现有诊断时序。P2/P2* 的解析、应用及与响应待定的关系留待后续需求，不在本步骤提前实现。

### 6.4 负响应识别与提示

在完整 UDS 消息收齐之后、正响应前缀核对之前，`DiagnosticTransactionService.ApplyTpResult` 增加通用负响应识别：

1. 验证当前事务身份、接收截止、LIN 校验和 NAD，按原链路记录原始报文。
2. 完整消息为 `7F + 原服务号 + NRC` 时，校验长度为 3 字节。
3. 原服务号应与本笔请求 SID 一致，本步为 `10`。例如 `7F 22 xx` 不作为本步的有效拒绝结果，应记录服务不匹配并按既有不匹配策略失败，不能借它刷新等待时间。
4. 保留原始 UDS、SID、NRC、中文原因和发生步骤；未知 NRC 也保留数值，不丢数据、不虚构含义。
5. NRC 非 `78`：将原始 UDS、NRC 和中文原因显示到升级日志，立即判定本次 OTA 失败，停止启动后续步骤；完成实际写入排空与收尾后退出 OTA 独占。
6. NRC `78`：不按终止失败处理，保留当前事务、保持 OTA 独占，按 §6.5 刷新截止并准备继续接收最终响应，不重发原 3C。

截图中的 NRC 建议建立统一映射，供后续 OTA 服务复用；不是要求 `10 03` 必须返回所有这些 NRC。

| NRC | 含义 / 建议中文提示 |
| --- | --- |
| `11` | 服务不支持 |
| `12` | 子功能不支持 |
| `13` | 消息长度错误或格式无效 |
| `21` | 设备忙，请求需稍后重试（本阶段不据此自动重发） |
| `22` | 执行条件不满足 |
| `24` | 请求顺序错误 |
| `31` | 请求参数超出范围 |
| `33` | 安全访问被拒绝 |
| `35` | 密钥无效 |
| `36` | 超过允许的尝试次数 |
| `37` | 要求的等待时间尚未结束 |

### 6.5 `78` 响应待定与 5 s 等待窗口刷新策略（2026-10-23 已实现）

#### 6.5.1 请求、响应与刷新事件

用户新增要求：收到 NRC `0x78` 后仍继续发送 3D，收到设备后续反馈时刷新 5 s 超时，重新计时。

术语按通信方向明确：上位机发送的是 3D 请求，收到的是中间件转回的 3D 响应。“每收到一次 3D 请求”在本策略中按“上位机收到 3D 返回的有效响应”理解。发送 3D、串口写入完成或没有回包本身，都不能刷新等待时间，否则设备完全不回复时会无限轮询。

用户已明确确认：只有收到本笔完整有效的 `7F 原请求SID 78`，才刷新 5 s 响应等待窗口，例如第七步的 `7F 10 78`。其他有效响应、FF/CF、普通接收字节以及发送 3D 本身均不刷新该窗口；FF/CF 的 N_Cr 仍按原 TP 规则独立计时，不与这 5 s 窗口混用。

有效 `78` 必须满足：属于仍活动的本笔诊断事务，NAD 与 LIN 校验正确，完整 UDS 长度为 3 字节，原 SID 与本笔请求一致，并且到达时仍在当前响应截止之内。不能凭原始字节流出现 `78` 判断待定，更不能将 NAD `78`、3C 回显或任意未认领数据作为刷新事件。

#### 6.5.2 时间规则

```text
t0 = 本笔 3C 串口写入完成时刻
初始 ResponseDeadline = t0 + 5 s

在当前截止前接收到一条有效 78：
    t_rx = 完整有效响应的软件接收单调时间
    ResponseDeadline = t_rx + 5 s

之后每收到一条有效 78：
    再以该条响应的接收时刻 + 5 s 替换当前截止
```

刷新从实际接收时刻起算，不从日志显示、UI 刷新或业务稍后处理时刻起算；只使用单调时钟。先检查当前截止，再决定是否接受响应并刷新：在截止时刻或之后才到达的 `78` 不得使已经超时的事务重新活动。

| 事件 | 响应截止 / 行为 |
| --- | --- |
| 3C 写完，尚未收到 `78` | 初始截止 t0 + 5 s |
| 每收到一条本笔有效 `78` | 改为本次接收时刻 + 5 s，保持本笔活动 |
| 单纯发送一次 3D 或 3D 写入完成 | 不刷新，不代表设备仍在响应 |
| 其他有效 SF/FF/CF 响应 | 不刷新 5 s 窗口；完整最终正响应按原成功条件结束，N_Cr 独立按原规则更新 |
| 错误 NAD、错误校验、残帧、错误原 SID、无活动事务的响应 | 不刷新，沿用既有过滤或失败规则 |
| 3C 回显 | 不刷新响应截止，仍单独核对回显 |
| 合法最终正响应 | 按原成功条件结束，不为了等待窗口而继续发满 5 s |
| 非 `78` 的有效负响应 | 日志提示原因，结束本次 OTA，不再等待 |
| 当前响应截止到期仍没有最终结果 | 超时失败、停新 3D、按既有策略收尾退出 |

例：假设有效回显已按时收到，以下均相对本笔 t0：

```text
0 s    3C 写完，初始截止 5 s
4 s    收到 7F 10 78，截止刷新为 9 s
8 s    再收到 7F 10 78，截止刷新为 13 s
10 s   收到合法 50 02 ...，本步成功，停止新 3D
       若 8 s 后一直无最终响应、也无新的有效 78，则 13 s 超时
```

此策略把原先固定的 5 s 总截止改成可由有效 `78` 续期的响应等待窗口，因此单笔总时长可能超过 5 s。当前未另设不可延长的整笔绝对上限或 `78` 次数上限；只要设备在每个有效窗口内持续返回有效 `78`，就持续等待。不要在实施时擅自加入一个原 t0 + 5 s 上限把等待提前截断。

#### 6.5.3 发送与事务生命周期

- 收到 `78` 后，仍按既有 20 ms 节拍发送 3D，忙则跳拍、不补发；只刷新截止，不因收到 `78` 把轮询节拍重新锚定。
- 不重发原始 3C，不重新调用一次 `ExecuteAsync`，不推进队列、OTA 步骤或探测成功/失败计数。
- 保留当前事务、原请求、连接代次及已经确认的 3C 回显状态，继续保持 OTA 独占；等待期间接收、解析和日志持续运行。
- 回显等待仍独立为 t0 + 1000 ms，`78` 不刷新它。收到 `78` 但原回显缺失时，仍按原回显截止失败。
- 最终正响应和有效回显共同决定成功；非 `78` 负响应、超时、断线、取消或释放仍按既有终止与排空规则收尾。
- 返回 P2/P2* 的数据继续不解析、不应用。本节的续期窗口明确为 5 s，不从设备时间字段动态取值。

#### 6.5.4 实施落点（已实现）

1. `ApplyTpResult` 在负响应分类后先判 NRC：`0x78` 进入续期分支，不再落入“任何完整负响应都 CompleteLocked”的路径；续期分支不发布最终结果，也不把 78 当成已验证正响应。
2. 收齐 `7F SID 78` 后立即 `transportProtocol.BeginReceive(...)` 重新准备接收（TP 此前的 `Completed` 状态会拒绝后续 PDU），保留外层事务、回显状态与串口共享缓存；同一字节块内紧跟的最终响应可依次进入。
3. 协调层在 `stateLock` 内刷新 `ResponseDeadline`；`LinBusScheduler.ExtendResponsePollingDeadline(ownerToken, deadline)` 校验轮询属主后替换 `pollDeadline` 并按原节拍续排，不重锚、不补发；若原截止已让轮询停止排拍，则按新截止重新激活。
4. 刷新与 `CompleteLocked` 在同一 `stateLock` 与同一事务身份下竞争，只允许一次最终完成；旧连接/旧事务的迟到响应不能刷新新事务期限。
5. `78` 在原始报文日志中正常保留；协调层通过 `ResponsePendingReceived` 事件（锁外触发）把 `DiagnosticResponsePendingNotice` 交给升级页，日志提示“设备处理中，响应等待已刷新”，不弹窗、不显示失败。

#### 6.5.5 验证范围与现状

- 无响应：即使每 20 ms 持续发 3D，仍在初始 5 s 截止，不因发请求而续期。
- 首条 `78` 在 4 s、下一条在 8 s：继续越过原 5 s 截止，最后在 13 s 无响应才超时。
- `78 → 正响应`、重复 `78 → 正响应`、`78 → 非78负响应`、`78 → 超时`，均只产生一次最终结果。
- 同一串口块内连续 `78` 与最终响应能够依次接收；错误 NAD、校验、原 SID、部分数据与回显不续期。
- 已进入 `78` 等待后，普通有效 SF/FF/CF 不刷新这 5 s；有效 CF 可独立刷新 N_Cr，但不能因此越过当前响应截止。
- 截止边界前后、延迟业务处理、旧代次回调、取消与断线竞争，以及 3D 调度器按新截止继续运行。
- 接收待定后不重复发 3C、不恢复应用帧、不重启回显预算、不自动进入下一步。

| 截止后到达的 78 | 已判超时，不重新激活、无通知 |
| 原 SID 不符的 `7F 22 78` | 判 `ResponseMismatch`，不续期 |
| 校验错误的 78 | 判 `DeadlineExceeded`，不续期 |
| 78 后非 78 负响应 | 判 `NegativeResponse`（NRC 0x22），续期 1 次，只发布一次结果 |
| 回显缺失 + 78 | 仍按 300 ms 回显窗口判 `EchoTimeout`；78 本身已续期 |
| 同一字节块 `78 + 50 03 ...` | 成功，且产生 1 次续期通知 |
| 连续两次 78 | 逐次续期，最后一次窗口到期后 2116 ms 才超时，通知 2 次 |
| OTA 全流程（第六步经历 78） | 九步全部完成，版本 `1.0/2.1/3.2`，升级日志含 78 续期提示 |

## 第七步：进入编程会话（已实现）

### 7.1 执行位置与前提

- 第六步扩展诊断会话成功且本笔收尾完成后，发送 `10 02`，请求进入编程会话。
- 沿用本次 OTA 的目标 NAD，持续保持 OTA 独占，不恢复应用帧，不额外增加步骤间固定等待。
- 用户确认本步骤与第六步基本一致：请求子功能由 `03` 改为 `02`，预期正响应由 `50 03` 改为 `50 02`，其余报文传输、回显核对、时间规则和失败处理复用第六步。
- 正响应后的 P2/P2* 四字节暂不处理，不用于修改任何计时。
- 非 `78` 的有效负响应记录日志后退出 OTA，不自动重试、不新增弹窗。
- NRC `78` 等待处理按 §6.5：不立即失败，保持本笔并继续 3D，收到有效 `78` 刷新响应等待窗口；已实现并由协调层统一处理（见 §6.9）。

提交本步的硬条件（全部满足才允许发起 `10 02`）：

| 条件 | 判定来源 | 不满足时的行为 |
| --- | --- | --- |
| 第六步 `10 03` 已成功 | `DiagnosticSessionService` 返回成功（6 字节 `50 03` + 有效回显） | 不提交 `10 02`，直接按第六步失败退出 OTA |
| 第六步本笔结果已发布且写入已排空 | `DiagnosticTransactionService` 已发布最终结果 | 等待收尾完成后再提交，不并发叠加第二笔事务 |
| 目标 NAD 与已发起步骤一致 | 本次 OTA 入参（页面输入框） | 同一次 OTA 内不允许换 NAD；不重新校验、不重新探测 |
| 串口仍连接、未被取消 | 连接状态与取消令牌 | 不提交新步骤，走既有取消/断线收尾 |

语义边界（避免把“进入编程会话”当成“可以开始写 Flash”）：

- 编程会话只是允许后续下载/编程类服务的前提状态，**不等于已解锁**；安全访问（`27`）、请求下载、数据传输、校验、复位等属于第八步及后续，不在本步骤内。
- 本步骤不发送 `10 01`、不复位设备、不解除诊断门禁，也不改变已建立的 OTA 独占。
- 进入编程会话后设备是否停止正常应用响应、是否触发内部复位、S3 时限是否仍然生效，当前**未确认**；本步骤不据此假设，也不额外发送任何保活帧（见 §7.6）。
- 本步骤不与第六步合并成一笔事务：两笔独立请求、独立回显核对、独立结果发布，失败归属分别记为第六步、第七步。

### 7.2 报文内容

以下使用默认 NAD `78`。请求及回显校验已重新计算；更换 NAD 时仍由构帧逻辑重新计算校验。

```text
发送 3C：55 AA 55 3C 08 78 02 10 02 FF FF FF FF 73
接收回显：               78 02 10 02 FF FF FF FF 73
发送 3D：55 AA 55 7D 00

正响应通式（PDU + CS）：78 06 50 02 P2_H P2_L P2STAR_H P2STAR_L CS
负响应通式（PDU + CS）：78 03 7F 10 NRC FF FF FF CS
```

若设备返回的后四字节也为 `00 32 01 F4`，对应正响应示例为：

```text
78 06 50 02 00 32 01 F4 07
```

这只是使用同一组会话时间数据的构帧示例，不表示设备编程会话时间参数已实测为该值；参数值不作为当前成功判据。负响应的原服务号仍为 `10`，负响应中不包含本次子功能 `02`，应由当前事务与步骤上下文关联，不凭 `7F 10 xx` 区分第六步和第七步。

请求 PDU 逐字节说明（3C 数据区 8 字节，不含外层的 `55 AA 55 3C 08` 与末尾 CS）：

| 偏移 | 字段 | 值 | 说明 |
| --- | --- | --- | --- |
| 0 | NAD | `78` | 本次 OTA 目标地址，取页面输入框 |
| 1 | SF PCI | `02` | 单帧，完整 UDS 长度 2（SID + 子功能） |
| 2 | SID | `10` | DiagnosticSessionControl |
| 3 | 子功能 | `02` | 编程会话；不使用抑制正响应位（bit7 必须为 0） |
| 4–7 | 填充 | `FF FF FF FF` | 与现有经典帧填充一致 |
| — | CS | `73` | 位于 8 字节数据区之后，即整帧第 14 字节；前 8 字节累加模 `0xFF` 后取反 |

经典校验复核过程（便于人工核对构帧）：

```text
0x78 + 0x02 + 0x10 + 0x02 + 0xFF × 4 = 1160 = 255 × 4 + 140
140 = 0x8C；0xFF − 0x8C = 0x73  → CS = 0x73
正响应示例：0x78 + 0x06 + 0x50 + 0x02 + 0x00 + 0x32 + 0x01 + 0xF4 = 503 = 255 × 1 + 248
248 = 0xF8；0xFF − 0xF8 = 0x07  → CS = 0x07
```

不同 NAD 下的请求 CS（回显 PDU 与请求相同，CS 亦相同，可直接用于比对预期回显）：

| NAD | 3C 请求 PDU | CS |
| --- | --- | --- |
| `0x78` | `78 02 10 02 FF FF FF FF` | `73` |
| `0x7A` | `7A 02 10 02 FF FF FF FF` | `71` |

构帧与判据的易错点（实现和自查时逐条核对）：

- 复制第六步代码时子功能若残留 `03`，报文会变成 `10 03`（本例 CS 应为 `0x72`），CS 仍用 `0x73` 会导致回显比对失败，容易被误判成设备无响应。
- 改了 NAD 却不重算 CS，同样会表现为回显不一致；CS 一律由构帧逻辑计算，不写死。
- 预期正响应前缀若残留 `50 03`，会把迟到的第六步响应误判为本步成功；本步前缀固定为 `50 02`。
- 子功能字节不得带 `0x80`（抑制正响应）；带上去后设备可能不返回 `50 02`，本步必然按超时失败。
- 3D 读取帧 `55 AA 55 7D 00` 与第六步完全相同，不随子功能变化。

### 7.3 单笔时序与成功条件

| 项目 | 规则 |
| --- | --- |
| t0 | 第七步本笔 3C 串口写入完成时刻 |
| 回显等待截止 | t0 + 1000 ms |
| 首次 3D / 后续轮询 | t0 + 20 ms / 每 20 ms 固定节拍，忙则跳拍 |
| 单笔响应截止 | 初始 t0 + 5 s；有效 `78` 按 §6.5 刷新为该次接收时刻 + 5 s |
| 回显核对 | 请求 PDU + 经典校验逐字节一致 |
| 正响应核对 | 完整 UDS 长度为 6 字节、前两字节为 `50 02`；后四字节不解析、不作参数数值校验 |
| 最终成功 | 有效回显与合法正响应均通过，完成收尾后交接第八步，保持 OTA 独占 |

回显与响应并行等待。正响应先验证通过时停止新的 3D，但仍须在原回显窗口内等有效回显；不能仅凭 `50 02` 就提前报告本步成功。响应缺失、回显缺失、格式错误等失败沿用第六步的失败退出与真实写入排空规则。

失败判定集合（本步与第六步一致，按现有协调层原因归类，不新增原因）：

| 现象 | 失败原因 | 是否继续后续步骤 |
| --- | --- | --- |
| 回显窗口内未收到逐字节一致的回显 | 回显超时/不匹配 | 否 |
| 无任何有效响应，直到 t0 + 5 s | 响应超时 | 否 |
| 完整 UDS 长度不是 6，或前两字节不是 `50 02` | 响应不匹配 | 否 |
| 迟到的 `50 03`（第六步响应） | 响应不匹配，不得判成功 | 否 |
| `7F 10 NRC`，NRC 非 `78` | 负响应（`NegativeResponse`） | 否 |
| 残缺 `7F` 或原 SID 不为 `10`（如 `7F 22 xx`） | 响应不匹配 | 否 |
| 串口断开、用户取消 | 断线/取消 | 否，走排空与独占释放 |

时序相关补充约定：

- 本步不因“刚进入扩展会话”而额外等待，也不在 `10 03` 成功后插入固定延迟；两笔事务之间只保留协调层既有的收尾与排空。
- `10 02` 的正响应到达即停止新的 3D 请求，但已发出的写入按既有规则排空，不中断在途帧。
- 本步时间参数全部取现有 `DiagnosticTiming.Default`，不因会话类型变化而调整；不使用 P2/P2* 返回值改写任何截止时间。
- 结果只发布一次，失败后不再重发 `10 02`，也不回头补发 `10 03`。

### 7.4 负响应日志与退出

复用第六步的 `DiagnosticNegativeResponse` 数据和 NRC 文案映射。非 `78` 的有效负响应显示本步骤、目标 NAD、原始 UDS、原请求 SID、NRC 与中文原因后，立即判定本次 OTA 失败，不执行第八步。

```text
第七步：进入编程会话失败。
设备负响应：7F 10 22；NRC=0x22，执行条件不满足；NAD=0x78。
```

未知且非 `78` 的 NRC 也显示十六进制值和原始数据后退出。停止新的 3C/3D，完成实际写入排空和状态清理后再退出 OTA 独占；连接有效时按既有策略恢复应用发送，断线则保持停止发送。不擅自发送 `10 01`、复位或其他恢复命令，不自动解除诊断门禁。

本步可能收到的负响应（仅用于文案核对，不预判设备一定返回其中之一；完整映射见 §6.4）：

| NRC | 中文提示 | 现场含义提示 |
| --- | --- | --- |
| `12` | 子功能不支持 | 设备可能只接受 `10 03`，需与 Bootloader 协议确认 |
| `13` | 消息长度错误或格式无效 | 检查 SF PCI 与填充字节 |
| `22` | 执行条件不满足 | 常见于前置条件（如未达到允许编程状态）不成立 |
| `33` | 安全访问被拒绝 | 若设备要求先解锁，需在第八步前补充安全访问 |
| `7E` | 当前会话不支持该子功能 | 检查是否仍在扩展会话 |
| 其他 | `NRC=0xXX，未知负响应` + 原始 UDS | 未知值只显示数值，不推断含义 |

日志格式固定为一条，不拆成多行、不省略 NAD：

```text
第七步：进入编程会话失败。
设备负响应：7F 10 5A；NRC=0x5A，未知负响应；NAD=0x7A。
```

- 失败阶段记为第七步（`OtaStage.ProgrammingSession`），不复用第六步的失败归属；同一笔只发布一次，避免日志重复。
- 失败结果是“第一至第六步已通过、卡在第七步”，由 `FailedStage` 表达即可，不回填、不清除前面步骤的成果，也不重发 `10 03`。
- `78` 按 §6.5 继续等待与刷新截止；协调层统一处理，第七步无需单独实现（见 §6.9）。

## 第九步：计算并发送 Key（27 0A，已实现）

### 9.1 用户提供的算法与 mask

用户提供的函数签名与参数为：

```c
uint32_t FLB_SeedToKey(uint8_t *wSeed, uint32_t flb_marsk);
static uint32_t s_securityMask = 0x3B61B270;
```

算法首先按 mask 的高字节到低字节提取 `3B 61 B2 70`，分别与原始 Seed 四字节 XOR：

```text
C0 = S0 XOR 3B
C1 = S1 XOR 61
C2 = S2 XOR B2
C3 = S3 XOR 70

K0 = ((C0 & 0F) << 4) |  (C1 & 0F)
K1 = ((C1 & F0) >> 4) | ((C2 & 0F) << 4)
K2 = ((C2 & F0) >> 4) |  (C3 & F0)
K3 =  (C3 & 0F)       | ((C0 & F0) >> 4)

返回值 = (K0 << 24) | (K1 << 16) | (K2 << 8) | K3
```

以上严格对应用户原式，不将 `K3` 改为看起来类似旋转或拼接的其他算法。用户补充说明提供的 `FLB_SeedToKey` 就是中间件使用的 Key 代码，上位机按该原式复现；`K3` 中两个操作数均位于低四位，结果高四位恒为 0，不据此擅自修改。不能因变量名 `wTop31Bits` 擅自截取 31 位。

用户已明确确认 Key 高字节先发送，线上顺序就是 `key_l[0]、key_l[1]、key_l[2]、key_l[3]`。若从函数返回的 uint32 提取，则依次右移 24、16、8、0 位并取低 8 位，不能使用依赖宿主端序的内存拷贝导致顺序颠倒。

### 9.2 演算向量（非实机样例）

仅用于核对原式的手算/脚本演算：

```text
Seed：12 34 56 78
Mask：3B 61 B2 70
Cal ：29 55 E4 08
key_l：95 45 0E 0A
函数返回数值：0x95450E0A
```

- 按已确认的高字节先发送规则，Key 为 `95 45 0E 0A`。
- 本向量用于核对原式及字节顺序，不能把演算结果当作设备已接受的解锁证据。

### 9.3 请求、回显与正响应

已确认的四字节 Key 请求格式：

```text
完整 UDS：27 0A K0 K1 K2 K3（K0 为返回 uint32 的最高字节）
发送 3C：55 AA 55 3C 08 NAD 06 27 0A K0 K1 K2 K3 CS
接收回显：               NAD 06 27 0A K0 K1 K2 K3 CS
发送 3D：55 AA 55 7D 00
预期正响应：67 0A（完整 UDS 长度恰好 2 字节）
```

四字节 Key 加 SID、子功能共 6 字节 UDS，仍为一个 SF，不需要 FF/CF，也没有额外 PDU 填充。Key 以四个二进制字节发送，不转成 ASCII 十六进制字符串。

设备已确认仅返回 `67 0A`，默认 NAD `78` 的串口响应为：

```text
78 02 67 0A FF FF FF FF 14
```

沿用上面的演算向量与已确认的高字节先发送顺序，完整 Key 请求示例为：

```text
55 AA 55 3C 08 78 06 27 0A 95 45 0E 0A 5D
```

该示例只适用于演算 Seed `12 34 56 78`，不作为可直接向实机发送的固定报文；实际 Seed 改变，Key 和经典校验均须重新计算。

只有有效请求回显与本步正响应均通过，才报告安全访问成功并交接第十步；算出 Key、完成串口写入或收到回显均不能单独视为解锁成功。

### 10.2 图片逐帧解析与完整请求

图片内容：

```text

78 21 00 54 00 00 00 5F
78 22 9C FF FF FF FF FF
```

| 分片 | NAD | PCI | 有效 UDS 数据 | 说明 |
| --- | --- | --- | --- | --- |
| FF | `78` | `10 0C` | `31 01 FF 00 00` | 总 UDS 长度 `0x00C = 12` 字节，首帧装前 5 字节 |
| CF1 | `78` | `21` | `00 54 00 00 00 5F` | 序号 1，追加 6 字节 |
| CF2 | `78` | `22` | `9C` | 序号 2，仅取最后 1 字节，其后五个 `FF` 为填充 |

重组为恰好 12 字节 UDS：

```text
31 01 FF 00 00 00 54 00 00 00 5F 9C
└───────┘ └─────────┘ └─────────┘
服务与RID   参数前四字节  参数后四字节
```

确定可识别的服务结构：

- `31`：RoutineControl。
- `01`：StartRoutine，启动例程。
- `FF 00`：例程标识 RID=`0xFF00`；本图片由用户说明用于擦除。
- 后八字节为此例程的控制参数，属于设备擦除契约，不能仅凭通用 RoutineControl 规则确定地址、长度或结束地址含义。

这三条 PDU 属于同一条完整请求、同一个诊断事务，不能拆成三次 `ExecuteAsync`，也不把最后的填充 `FF` 加入 UDS 消息。

### 10.3 地址、长度与固件映像的关联

用户确认擦除参数是本次固件的起始地址和大小，不是固定 APP 全区，也不是固定截图数值。按图片的“大端四字节起始地址 + 大端四字节字节长度”布局设计，截图示例对应：

| 字段 | 图片字节 | 示例值 |
| --- | --- | --- |
| 起始地址 | `00 00 54 00` | `0x00005400`，十进制 21504 |
| 擦除字节长度 | `00 00 5F 9C` | `0x00005F9C`，十进制 24476 字节 |
| 最后一个字节地址 | `start + length - 1` | `0x0000B39B` |
| 结束边界（不含） | `start + length` | `0x0000B39C` |

`0x5400/0x5F9C` 只描述这张图片使用的固件。正式请求每次按加载固件重新生成：`31 01 FF 00 + 起始地址四字节 + 大小四字节`，不能把截图数值写死，也不把结束地址作为大小发送。

固件模型关联按当前源码梳理如下；其中 BIN 地址来源仍待确认，HEX 的范围换算为基于现有归一化映像的方案：

| 文件格式 | 地址来源 | 大小来源 / 注意事项 |
| --- | --- | --- |
| HEX | 现有 `FirmwareImage.BaseAddress`，即最低数据记录地址 | 建议使用归一化映像 `ImageSize = Data.Length`，等于最高地址 - 最低地址 + 1；包含段间填充空洞，不使用 HEX 文本文件的 `FileSize` |
| BIN | 原始 BIN 没有地址信息，实际烧录起始地址来源待确认 | 数据大小为 `Data.Length`，通常等于 BIN 文件字节数；现有模型 `BaseAddress=0` 是加载默认值，不是设备擦除地址已确定为 0 |

若用户要求 HEX 仅对各独立数据段擦除，或文件存在 Bootloader/配置等非 APP 段，应另行明确分段/筛选规则；本轮不擅自丢弃地址段，也不把多个段的有效字节数相加当作连续范围长度。HEX 的入口地址字段不替代最低数据地址。

图片中不存在地址/长度格式标识 `44`。本设计不会照搬其他 ECU 示例而自行插入 `44`；若设备需要格式标识，应重新核对实际擦除协议和总消息长度。

范围确认后，上位机在第十步提交前生成一份不可变的擦除参数快照，并核对：

1. 地址字节序、长度单位与溢出；长度必须符合已确认的设备约束。
2. 范围处于设备允许的 APP 分区，不能覆盖未授权的 Bootloader、配置或保留区。
3. 是否按 Flash 页/扇区对齐、设备内部是否自动扩展到页边界；没有契约时不擅自向下/向上扩展。
4. 范围随固件计算：明确 BIN 的实际烧录地址、HEX 的有效地址范围及空洞处理，区分归一化映像字节数和磁盘文本大小。现有 BIN 模型的 `BaseAddress=0` 不代表设备 APP 地址为 0。
5. 擦除参数与后续下载使用同一份固件映像/目标地址快照，不在两步之间因重新加载文件或修改 NAD 而改变。

起始地址和大小的动态来源原则已经确定。BIN 起始地址由哪里提供、HEX 空洞是否按现有归一化映像处理，以及设备分区/页边界约束仍需按实际使用范围细化，不增加猜测值；设备擦除完成响应另见 §10.6。

**实现落点（2026-10-23）**：`ErasePlan.TryCreate` 只对四条可判定的规则做硬校验——`BIN` 直接拒绝、`BaseAddress` 必须落在 `0..0xFFFFFFFF`、`ImageSize` 必须大于 0 且不超过四字节长度字段、`BaseAddress + Length` 不得越过 32 位地址空间。需要设备契约的规则（APP 分区、页/扇区对齐、是否自动扩展到页边界）没有擅自实现，也没有向下/向上取整。参数在第十步入口一次生成，之后不再读界面或重新加载文件；后续下载步骤应复用同一份快照。

### 10.4 上位机串口封装与回显

按本项目固定串口封装，每一条 PDU 都经同一个 3C 出口发送，并等待对应 PDU + CS 的回显。默认 NAD `78` 的三条请求及经典校验已计算为：

```text
FF ：55 AA 55 3C 08 78 10 0C 31 01 FF 00 00 39
CF1：55 AA 55 3C 08 78 21 00 54 00 00 00 5F B2
CF2：55 AA 55 3C 08 78 22 9C FF FF FF FF FF C8
```

对应回显分别为：

```text
78 10 0C 31 01 FF 00 00 39
78 21 00 54 00 00 00 5F B2
78 22 9C FF FF FF FF FF C8
```

最后一个 `FF` 可能是填充，但仍参与每条 PDU 的经典校验。更换 NAD 或任何擦除参数后，分包内容与校验均应通过既有 TP/Codec 重新生成，不复制这些固定报文作为实现。

### 10.5 请求发送与响应等待设计

```text
第九步安全访问成功
    → 固化并验证擦除范围参数
    → 生成一条 12 字节 UDS 请求
    → 现有 LIN-TP 分包为 FF、CF1、CF2
    → 发 FF，核对回显
    → 发 CF1，核对回显
    → 发 CF2，核对回显
    → 按既有多帧路径完成固定回显隔离
    → 启动 3D 轮询，等待擦除结果
        ├─ 有效 7F 31 78 → 保持本笔，刷新 5 s，继续 3D
        ├─ 非78有效负响应 → 日志显示后失败退出
        ├─ 当前窗口到期 → 超时失败退出
        └─ 已确认的擦除完成正响应 → 本步成功，交接第十一步
```

复用 `DiagnosticRequest` 与显式 `DiagnosticMultiFrameOptions`，由新增擦除业务负责请求参数和响应语义，事务层负责回显、截止、续收及排空。请求不能因长度超过 6 字节就继续使用 SF 的整笔 t0 定义。

建议先复用当前多帧默认参数作为设计基线，需按中间件与 Bootloader 确认实际时序：

| 项目 | 当前多帧默认值 / 本步方案 |
| --- | --- |
| 单片写入等待预算 | 500 ms |
| 单片回显预算 | 1000 ms，按现有多帧提交时刻规则计时 |
| 分片最小间隔 | 0 ms，但仍需等待本片有效回显后再发下一片 |
| 最大相邻分片间隔预算 | 1000 ms |
| 请求发送总预算 | 按片数与现有公式计算，独立于响应等待窗口 |
| 全部请求完成时刻 t_last | 最后一片写入完成与最后回显确认二者的较晚时刻 |
| 回显隔离 | 自 t_last 起 50 ms；其间不发新的 3C/3D |
| 首个 3D | 不早于隔离结束与 t_last + 20 ms 两者的较晚时刻；默认约为 t_last + 50 ms |
| 后续 3D | 每 20 ms 固定节拍，忙则跳拍、不补发 |
| 初始响应截止 | t_last + 5 s，包含隔离时间 |
| 有效 NRC 78 | 仅 `7F 31 78` 按完整响应接收时刻 + 5 s 刷新截止，不重发擦除请求 |
| 其他响应与写入 | 不刷新这 5 s；接收多帧响应时 N_Cr 独立为 1000 ms |

当前请求发送与回显隔离期间不发 3D，因此不能提前读取 FF 后设备就产生的拒绝结果。需要确认设备容忍剩余 CF，并将最终响应保留到主机开始读取；若设备要求发送期穿插 3D，须单独修订既有多帧契约，不能无依据混用。

### 10.6 擦除成功判据与负响应

通用 RoutineControl 正响应结构为 `71 + 控制类型回显 + RID回显 + 可选状态记录`。因此本步应首先核对 `71 01 FF 00`，但仅有这个前缀不能自行证明 Flash 已擦除完毕；设备的状态记录、长度和返回时机必须确认。

已向用户询问实际完整响应，例如：

- `71 01 FF 00` 是否已表示擦除完成；
- 是否返回 `71 01 FF 00 00` 等附加结果字节，以及各值的含义；
- 是否只表示“接受/启动擦除”，还需 `31 03 FF 00` 查询最终结果。

在确认前，不硬编码附加 `00` 为成功，不自行新增查询请求，也不将“启动例程已接受”显示为“擦除完成”。有效中间件回显只确认请求反馈，同样不能作为擦除成功。

负响应必须匹配原请求 SID `31`：

```text
7F 31 78 → 设备处理中，按 §6.5 续期和继续3D
7F 31 NRC（NRC非78）→ 记录原始数据、NRC、中文原因，退出本次OTA
```

其他 SID 的旧响应不认作本次擦除结果，不刷新等待；错误校验、错误 NAD 和部分字节不续期。超时、断线或取消后的擦除执行状态可能未知，不能自动重发擦除或重复提交同一请求；沿用真实写入排空和 OTA 退出规则，设备复位或退会话动作不擅自增加。

**实现判据（2026-10-23）**：`EraseFlashService` 只核对 `71 01 FF 00` 四字节前缀（长度不足或前缀不符按 `ResponseMismatch` 失败）；`71` 之后的内容原样保存在 `EraseResult.StateRecord` 与 `OtaEraseOutcome.StateRecord`，不解释、不比较、不补 `00`。`OtaEraseOutcome.CompletionConfirmed` 恒为 `false`，升级日志与结果文案只写“请求已被设备接受”。契约确认后只需改该字段与本节判据，不必调整请求构造和事务层。

### 11.2 74响应与块大小

完整 UDS 为 `74 40 00 00 00 82`：`40` 的高四位4表示后续长度字段占4字节，`00000082`按大端为130。

结合图片2首帧的 `10 82`，本例一条36请求的UDS总长130字节，由 `36` 一字节、块序号一字节、固件数据128字节组成。130不是纯固件数据长度。

用户已确认本次解析正确：每条36最大UDS块长130字节，包含SID和块号两字节，每包最多128字节固件数据；最后一块可以少于128字节，按实际文件剩余大小安排。

应解析本次74返回的容量：`DevicePayloadCapacity = maxNumberOfBlockLength - 2`，本例为 `130 - 2 = 128`，不把130当成纯固件大小，也不忽略设备返回值。按本阶段每包最多128字节的约束，实际数据块容量不超过128，且不得超过设备本次返回容量；若返回更小，受更小值限制。

解析需校验长度格式、字段是否完整、数值范围、块长大于2及UDS总长不超过本项目LIN-TP上限4095；不能静默截断文件或拼出超长请求。

## 第十二步：逐块传输固件（已实现）

### 12.1 图片2：一块对应一笔36事务

关键首尾报文如下：

```text
[3C] 78 10 82 36 01 70 15 00
[3C] 78 21 20 55 55 00 00 63
……
[3C] 78 2F ...   ← LIN连续帧序号15
[3C] 78 20 ...   ← LIN连续帧序号0，4位回绕
[3C] 78 21 ...   ← LIN连续帧序号1
……
[3C] 78 25 00 6D 55 00 00 FF
[7D] 78 02 76 01 FF FF FF FF
```

本块UDS为 `36 01 + 128字节固件`，共130字节。`01` 是 blockSequenceCounter，不是子功能；首帧装 `36 01` 和头3字节固件。总分片数为 `1 + ceil((130 - 5) / 6) = 22`，即1FF+21CF；最后CF有5字节有效UDS数据，末尾FF仅为TP填充，不计入固件128字节。

图片中部分行右侧另有校验列，不与黄色区域的固定8字节PDU混为一条UDS。实际串口校验仍由既有Codec计算。

本块确认UDS为 `76 01`，默认NAD的串口响应为 `78 02 76 01 FF FF FF FF 0E`。必须核对76回显的块号与当前块号一致；迟到或错号响应不能推进偏移和进度。按图片建议正响应恰好两字节 `76 BSC`，若设备附带其他字段，应补充格式。

### 12.2 两层分包及确认顺序

```text
同一份固件Data → 按74容量切成固件块
    → 构造36 + 块号 + 本块字节
    → LIN-TP拆FF/CF，经3C逐片发送并核对回显
    → 本块所有分片完成、隔离结束
    → 3D读取，取得本块76确认
    → 更新已确认偏移和块号
    → 下一块，直至全文件确认
```

每条36的全部LIN分片及其76响应是一笔诊断事务。不能将每个CF当作一个固件块，也不能先发完整份文件再统一读一次3D。全过程保持OTA独占，块间不恢复应用帧、不插入其他诊断。

| 序号 | 用途与方案 |
| --- | --- |
| UDS块号 | 8位，第一块01；每个新块成功后加一，按 `...FE FF 00 01...` 回绕，若设备有差异须明确 |
| LIN CF序号 | 4位，每条新UDS内部重新从1开始，按 `...F 0 1...` 回绕 |

每条76确认后才增加已确认固件字节数。串口写入完成、中间件回显和PDU发送数量，不等于本块业务确认或全文件校验通过。

### 12.3 末块、填充与示例数量

若文件大小24476字节、每块数据128字节，则 `24476 = 191 × 128 + 28`：共192块，末块28字节，块号为C0。本例尚未触发8位块号回绕。

用户已确认末块只发送剩余有效字节，不补满128字节。本例为 `36 C0 + 28字节`，UDS总长30字节，分为1FF+5CF。每次取数长度为 `min(本次块容量, 固件总长度 - 当前偏移)`，只有最后一块可以因剩余字节不足而缩短。

LIN-TP仍在最后PDU不足8字节时按原协议填FF，但这些填充不计入固件长度、已确认进度或UDS声明长度；不在固件数据层额外补齐，不写出申请的固件范围。

### 12.4 78、失败和重传

- 每块显式提供多帧选项，复用现有发送预算、逐片回显、隔离与3D调度。
- 片间隔：块内相邻 3C 分片的最小发送间隔固定为 20 ms（`FirmwareDownloadService.FrameGap`），自上一片串口写入完成起算。实测单片回显约 11～12 ms，因此实际 TX→TX 约 20 ms；该值只作用于 `36` 多帧请求，`34`、`37`、`31` 仍用默认 0 ms。
- 块间间隔：上一块 `76` 确认返回后固定等待 10 ms，再提交下一块 `36`（`OtaUpgradeService.BlockInterval`）。首块之前不等待；块内分片间隔见上一条；该等待不改变 5 s 响应预算，也不恢复应用帧。

### 13.2 图片与完整串口报文

接收正响应：             78 01 77 FF FF FF FF FF 0F

| 项目 | 规则 |

## 第十四步：固件校验（31 01 02 02，已实现）

### 14.1 执行前提与已确认结果

第十三步结束传输已取得有效77及请求回显、事务收尾完成后，再执行固件校验。沿用本次NAD、同一固件数据与范围快照，持续保持OTA独占。

用户提供的图片中，最终响应的结果字节已明确：`00` 表示校验成功，`01` 表示校验失败。本节自 2026-10-23 起已编码（§14.8），实机未验证。

### 14.2 图片逐帧解析

```text
[3C] 78 10 10 31 01 02 02 00
[3C] 78 21 00 54 00 00 00 5F
[3C] 78 22 9C B0 05 1F 35 FF
[7D] 78 03 7F 31 78 FF FF FF  ← 待定响应，继续读取
……3D轮询……
[7D] 78 05 71 01 02 02 00 FF  ← 结果00，校验成功
```

第一行PCI `10 10` 表示UDS总长 `0x010＝16` 字节；FF装前5字节、CF1装6字节、CF2只取最后5字节，第三行末尾FF仅为TP填充。

完整请求重组为：

```text
31 01 02 02 | 00 00 54 00 | 00 00 5F 9C | B0 05 1F 35
```

| 字段 | 示例 | 解释与确认状态 |
| --- | --- | --- |
| SID / 控制类型 | `31 01` | RoutineControl / StartRoutine |
| RID | `02 02` | 本设备固件校验例程0x0202 |
| 地址 | `00 00 54 00` | 沿用前面固件地址，示例0x5400 |
| 大小 | `00 00 5F 9C` | 沿用实际传输范围，示例24476字节 |
| CRC32 | `B0 05 1F 35` | 用户确认本次固件CRC32，按此字节顺序发送；不硬编码示例值，算法/范围按两端实际实现核对 |

这是同一条16字节UDS多帧请求，共1FF+2CF，不拆成三笔事务。RID不同于第十步擦除的FF00；校验请求也不使用下载34中的44格式标识。

### 14.3 默认NAD下的完整串口报文

按截图参数补齐既有串口封装与经典校验：

```text
FF ：55 AA 55 3C 08 78 10 10 31 01 02 02 00 31
CF1：55 AA 55 3C 08 78 21 00 54 00 00 00 5F B2
CF2：55 AA 55 3C 08 78 22 9C B0 05 1F 35 FF BE
```

每片回显为该请求的8字节PDU加最后CS，不带串口头。仍逐片核对回显，全部完成及隔离后才开始3D轮询。

```text
发送3D：55 AA 55 7D 00
待定响应：78 03 7F 31 78 FF FF FF 5B
成功响应：78 05 71 01 02 02 00 FF 0C
失败响应：78 05 71 01 02 02 01 FF 0B
```

失败响应是将用户已确认的状态01代入同一格式计算得到的示例。换NAD、地址、大小或四字节校验数据后，分片与CS必须重新生成。

### 14.4 成功、业务失败与负响应的区分

完整最终UDS应恰好5字节：`71 01 02 02 Result`。先核对长度、SID、控制类型、RID，再读取第5字节结果，不能只检查 `71 01 02 02` 前缀即报告成功。

| 收到的完整UDS | 业务处理 |
| --- | --- |
| `71 01 02 02 00` | 校验通过；有效回显也已确认后，本步成功 |
| `71 01 02 02 01` | 校验失败，记录原始响应及“固件校验失败”并退出OTA，不执行后续步骤 |
| `71 01 02 02` 缺结果字节 | 响应格式错误，不判成功 |
| `71 01 FF 00 ...` 等其他RID | 不属于本步最终结果，不能误认校验成功 |
| `71 01 02 02` 后其他未定义结果值 | 记录未知结果的十六进制值并按失败处理，不默认成功 |
| `7F 31 78` | 仍在处理，刷新5s等待并继续3D，不发布终止结果 |
| `7F 31 NRC`，NRC非78 | 负响应，日志显示原始UDS/NRC/中文原因后退出OTA |

`71 ... 01` 在UDS服务层属于肯定响应，但例程执行结果为失败；不能把结果01伪装成NRC=01。与 `7F 31 xx` 的结构化负响应分别保存，界面均应准确说明失败原因。

最终合法响应到达后停止新的3D；有效回显与最终结果的共同完成、真实在途写入排空、取消/断线和独占释放沿用已有规则。校验失败不自动重擦除、重传文件或复位设备。

### 14.5 78与时间规则

本步骤是16字节多帧请求，复用第十步的多帧配置与时间语义：逐片写入/回显预算、请求发送总预算及回显隔离独立于响应窗口；初始响应截止从最后写入与最后回显均完成的时刻起算5s，包含隔离时间。默认隔离50ms，随后首次3D不早于隔离结束，后续每20ms轮询。

图片中的 `7F 31 78` 明确进入已有§6.5处理：只要是在当前截止前收到的本笔有效78，就把响应截止改为该次接收时刻+5s；保持同一事务和OTA独占，不重发校验3C、不重新提交请求、不推进步骤。

图片中的空白7D行不能解释为上位机停止轮询，也不能据截图无时间戳推断实际处理时长；无回复仍继续按已定节拍读，只有有效78续期。普通字节、发3D、回显或最终响应的到达不刷新这5s。

### 14.6 已确认的CRC32及两端一致性核对

用户已明确确认：

- `B0 05 1F 35` 是这一次固件升级使用的CRC32值。
- 校验结果按 `B0 → 05 → 1F → 35` 字节顺序传输。若以uint32数值 `0xB0051F35` 表示，构帧时按高字节先发送，不能直接依赖宿主内存端序。
- CRC32的多项式、初值、最终异或以及计算范围，以当前上位机和Bootloader的实际实现为准；两端必须一致。

当前上位机源码已核对：`FirmwareCrc32.Compute` 使用反射多项式 `0xEDB88320`、初值 `0xFFFFFFFF`，按字节更新后最终取反（等效最终异或 `0xFFFFFFFF`）；输入为 `FirmwareImage.Data` 全部归一化映像字节，HEX地址空洞已经填FF。现有页面值原本用于显示，是否可直接用于本步，要在核对Bootloader实现后确认。

本次用户回复确认了CRC32类型、传输顺序和一致性要求，不等同于已经读取Bootloader代码或验证两端参数完全一致。实施前需核对：

| 核对项 | 要求 |
| --- | --- |
| 算法 | 上位机与Bootloader的多项式、初值、位序、最终异或/取反一致 |
| 输入范围 | 实际下载的地址、长度及字节内容一致；核对HEX空洞、文件内头尾/校验字段、设备侧补齐是否参与 |
| 字节顺序 | uint32结果按最高字节到最低字节发送，与示例B0 05 1F 35一致 |
| 固件快照 | 计算CRC、构造地址/大小与分块传输使用同一份固件数据，不中途换文件或复用其他固件CRC |
| 示例验证 | 在取得对应固件数据或设备实现后，复算是否得到0xB0051F35；目前仅有报文，尚未复算该固件CRC |

不将 `B0 05 1F 35` 固定用于所有固件。正常设计不包含36服务号、块号、NAD、PCI、串口头、LIN校验和TP填充；若设备实际计算范围有专门约定，则必须同步核对上位机的数据范围。不能在两端差异未厘清时发送猜测校验值，也不能将“一致性要求已确定”写成“Bootloader一致性已验证”。

- **算法复用**：`FirmwareCrc32` 由 `Services/FirmwareFileService.cs` 移入 `Models/FirmwareCrc32.cs`（同为 `internal`），使参数模型可在不反向依赖服务层的前提下按快照数据复算 CRC32；多项式 0xEDB88320、初值 0xFFFFFFFF、最终取反不变，页面显示值与第十四步请求值同出一源。
- **请求与解析**：`Services/FirmwareVerificationService.VerifyAsync` 构造 16 字节 `31 01 02 02 + 地址 + 大小 + CRC32`（CRC 用 `WriteUInt32BigEndian`，不依赖宿主端序），只接受完整 5 字节 `71 01 02 02 Result`；00 通过、01 业务失败（不当成 NRC=01）、其他结果值记录十六进制并按失败处理。
- **验证（82 项中的第十四步部分）**：16 字节请求的地址/大小与第十二步一致、CRC32 与独立实现的高字节先发值一致；结果 00 通过、01 失败、07 未知失败、缺结果字节按格式错误；`7F 31 78` → 继续等待 → `00` 成功。
- 未实机验证；Bootloader 侧 CRC32 参数与计算范围仍待与上位机逐项核对（§14.6）。

## 第十五步：设备复位（11 01 / 51 01）

### 15.1 执行位置与图片解析

第十四步收到合法 `71 01 02 02 00`、有效请求回显且事务收尾完成后，才进入本步。校验结果01、其他失败、断线或取消均不发送复位。步骤交接继续保持本次NAD与OTA独占。

用户提供的图片为8字节LIN诊断PDU：

```text
[3C] 78 02 11 01 FF FF FF FF
[7D] 78 02 51 01 FF FF FF FF
```

| 字段 | 解释 |
| --- | --- |
| `78` | 示例NAD，实际沿用本次OTA目标地址 |
| `02` | SF有效UDS长度2字节 |
| 请求 `11 01` | ECU复位服务，子功能01 |
| 正响应 `51 01` | 复位肯定响应，回显子功能01 |
| 四个FF | TP填充，不属于有效UDS消息 |

请求与响应均为SF，不带CRC32、固件地址、大小或下载块序号。

### 15.2 完整串口收发内容

默认NAD=`78`时，补齐本项目串口头与经典校验后：

```text
发送3C：55 AA 55 3C 08 78 02 11 01 FF FF FF FF 73
接收回显：               78 02 11 01 FF FF FF FF 73
发送3D：55 AA 55 7D 00
接收正响应：             78 02 51 01 FF FF FF FF 33
```

请求/回显CS=`73`，正响应CS=`33`，仅计算完整8字节PDU；其他NAD由既有Codec重新构帧计算。图片中的7D是响应读取标记，不能省略上位机实际的3D读取请求。

### 15.3 时序与最终成功

沿用此前SF诊断规则，不为本步新建发送出口或计时器体系：

| 项目 | 规则 |
| --- | --- |
| t0 | 本笔11 01的3C串口写入完成时刻 |
| 回显等待截止 | t0 + 1000ms |
| 首次3D / 后续节拍 | t0 + 20ms / 每20ms，忙则跳拍；与回显等待并行 |
| 初始响应截止 | t0 + 5s |
| 有效待定响应 | `7F 11 78` 按接收时刻续期5s，继续3D，不重发11 01 |
| 最终成功 | 有效3C回显通过，且完整UDS恰好为两字节51 01 |

51 01先到时停止新的3D，但仍在原回显窗口内等有效回显；仅有回显、仅串口写完或仅通信暂时消失均不能判成功。51 02等其他子功能、错误长度或校验不能误认成功。

### 15.4 负响应与异常退出

- 有效非78负响应为 `7F 11 NRC`：日志显示步骤、NAD、原始UDS、NRC与中文原因，终止本次OTA，不自动重新复位。
- 只有有效 `7F 11 78` 刷新5s；普通字节、3D提交、回显和无响应不刷新。
- 设备在未取得合法51 01之前失联，仍按既有断线/超时返回失败或未确认，不能因为“可能已经复位”就假报成功。
- 停止新3C/3D，真实写入排空后释放OTA独占；连接仍有效时恢复应用发送，断线则保持停止。不自动发送10 01或再次执行安全访问、擦除、下载。
- 失败日志标明发生在第十五步，保留前面文件传输与校验结果，不将前序成功记录清零。

### 15.5 流程完成与启动验证边界

本步最终成功后，停止本笔新3D，完成接收上下文、计时与真实在途写入收尾，再结束OTA独占。当前既有恢复应用发送机制可复用；复位确认后固定等待 50 ms 读取一次 APP 版本（§15.7），仍不新增自动重连，也不自动判定“启动成功”。

界面显示“十五步升级报文流程完成，设备已返回复位肯定响应”；若复位后那次 APP 版本读取成功，完成状态行改为“升级完成，复位后 APP 版本 <版本>”。原始报文及各步骤结果保留。该结论与“新固件已经启动并正常运行”分开：后者需实机通过启动后的通信、版本或设备行为验证，不将51 01等同于已经观察到启动成功，也不把一次版本读取当成完整启动判据。

若后续需要软件自动判定启动成功，再另行明确复位后等待时间、重试次数、探测方式与预期版本；本次只按用户要求做“等 50 ms 读一次 APP 版本”，不增加第十六步。

### 15.6 实现与验证状态（2026-10-23）

- **业务层**：新增 `Services/EcuResetService.cs`，只构造两字节 `11 01` 请求并核对完整正响应恰为 `51 01`；`EcuResetResult` 保留原始负响应、补充说明与请求字节。回显核对、3D 轮询、超时与 `7F 11 78` 续期全部复用 `DiagnosticTransactionService`，未新增发送出口、未新建计时器体系。
- **编排**：`OtaUpgradeService` 在第十四步成功后进入 `OtaStage.EcuReset = 15`，`Completed` 顺延为 16；复位失败时保留擦除、下载与校验结果，只记失败阶段，不清零前序成果。复位成功只上报“设备已返回复位肯定响应”，不写“新固件已启动”。
- **状态与界面**：`OtaSessionResult` 增加 `ResetOutcome`；升级页增加 `OTA-15` 日志标签、第十五步状态文案与 99% 进度，完成后状态行显示“十五步升级报文流程完成，设备已返回复位肯定响应”。
- **验证（33 项，串口替身，连跑 5 次一致）**：`OtaStage` 编号 15/16；完整流程中 `11 01` 位于最后的 `31 01 02 02` 之后且只发一次，整帧为 `55 AA 55 3C 08 78 02 11 01 FF FF FF FF 73`，复位后仍有 3D 读取；校验结果 01 时不发复位；`7F 11 22`、`51 02`、无响应三种情形均判失败且不重发，`7F 11 78 → 51 01` 续收后成功，失败日志含步骤、NAD、原始 UDS 与 NRC。
- 未实机验证：真实复位后的总线行为（设备重启期间应用帧恢复）、不同 Bootloader 的复位子功能约定、复位响应与设备实际重启的时序，均需实机确认。第一至第十四步的既有检查结果不覆盖本步。

### 15.7 复位后 APP 版本确认（2026-10-23 追加，已实现）

用户要求：复位成功后等待 50 ms，再查询 APP（软件）版本号。

| 项目 | 内容 |
| --- | --- |
| 触发条件 | 仅当第十五步收到恰好 `51 01` 之后；复位失败或未确认时不执行 |
| 等待 | **50 ms**，自 `51 01` 到达时刻起算（`OtaUpgradeService.ResetVersionDelay`） |
| 请求 | `22 F1 95`，与第二步同一 DID、同一 `DeviceInformationService.ReadVersionAsync(Firmware)`，复用既有 SF 时序 |
| 时序 | t0+20 ms 首拍、20 ms 节拍、回显 1000 ms、总截止 5 s；设备在截止前给出完整 `62 F1 95 + 版本数据` 即成功 |
| 成功 | 日志 `[OTA-15] 复位后等待 50 ms 读取 APP 版本成功：<版本>`；写入 `OtaResetOutcome.AppVersionAfterReset`；完成状态行显示“升级完成，复位后 APP 版本 <版本>” |
| 失败 | 只记一条 Warning（含原始失败原因），**不判本次升级失败**、不重试、不重连；`AppVersionAfterReset = null`，完成状态行回落到“十五步升级报文流程完成，设备已返回复位肯定响应” |
| 边界 | 读到的版本只证明复位后设备可通信并能返回该 DID；不据此断言“新固件已启动运行”，也不新增第十六步 |

失败为什么不判失败：`51 01` 已确认复位被接受，而设备复位后可能仍在启动，一次版本读取失败不足以推翻“固件已写入并通过 CRC32 校验”的事实；因此只作为提示保留。若后续需要严格的启动判定，应另行约定重试次数、等待时长与预期版本。

该读取为新增改动，未纳入第十五步原有的 33 项离线检查，实机未验证。
