# 诊断模块并发缺陷修复说明

修复日期：2026-10-18。

本文记录针对诊断模块第一阶段实现中 5 个并发缺陷（P1 级）的修复内容、影响范围、验证方式，以及如何确保原有功能与后续诊断功能不受影响。

---

## 1. 背景与问题清单

诊断第一阶段实现后，经并发审查发现 5 个 P1 级缺陷，均属并发/时序类问题，可能导致死锁、发送出口卡死、状态机错乱、跨断线重放旧请求、超时判定失效：

| 编号 | 问题 | 位置（修复前） | 严重性 |
| --- | --- | --- | --- |
| #1 | 锁顺序反转，可导致死锁 | `LinFrameChannel.HandleBytesReceived` 持通道锁分发回调；发送路径持调度锁申请通道锁 | P1 致命 |
| #2 | 同步完成的写入会让发送出口永久"占用" | `LinBusScheduler.SendDiagnosticRequestAsync` 先启动任务后赋 `activeSendTask` | P1 致命 |
| #3 | 旧队列循环收尾可能破坏新事务 | `DiagnosticTransactionService.ProcessQueueAsync` 的 `finally` 无条件清共享状态 | P1 |
| #4 | 出队后等待进入独占的诊断可跨断线重连继续发送 | `ProcessQueueAsync` 出队后、登记 `active` 前的窗口 | P1 |
| #5 | 接收路径没有执行硬截止检查 | `HandleDiagnosticPacket` 直接确认回显/完成响应 | P1 |

---

## 2. 改动内容

### 2.1 #1 锁顺序反转死锁

**根因**：存在两条锁获取顺序相反的路径，构成死锁环：

```text
发送路径：调度器锁 → 通道锁（PollTimerCallback → channel.Send* → WriteAsync 的 lock(stateLock)）
接收路径：通道锁 → 协调层锁 → 调度锁（HandleBytesReceived → parser.Append → 回调 → CompleteLocked → scheduler.StopResponsePolling）
```

**修复**（`LinFrameChannel.cs`）：

- `HandleBytesReceived`：不在通道锁内调用 `parser.Append`，改为在锁内只做轻量的 `isConnected && !disposed` 状态读取，出锁后再 `parser.Append`。`parser` 自身有 `bufferedBytes` 锁保证线程安全，无需通道锁兜底。
- `HandleConnectionStateChanged`：连接状态事件 `ConnectionStateChanged?.Invoke(connected)` 移出通道锁外触发。
- `Dispose`：`ConnectionStateChanged?.Invoke(false)` 移出锁外。

修复后锁序统一为单向：**协调层锁 → 调度器锁 → 通道锁（仅叶子写入）**，接收回调不再在通道锁内跨层申请其他锁，死锁环消除。

### 2.2 #2 同步完成写入导致出口永久占用

**根因**：`SendDiagnosticRequestCoreAsync` 是 `async` 方法，当底层 `SendAsync` 返回已完成 Task 时，方法在首次真实 `await` 前同步跑完，其 `finally` 同步执行 `ClearSendTask`，随后调用方 `activeSendTask = task` 又把已完成任务赋回，导致出口永远非空。

**修复**（`LinBusScheduler.cs`）：

- 新增独立的 `sendBusy` 标志与 `sendGeneration` 代次计数，把"是否占用"与"任务引用"解耦。
- `SendDiagnosticRequestAsync`：在锁内先 `sendBusy = true`、`++sendGeneration`，再启动任务并赋 `activeSendTask`。占用判断改用 `sendBusy`。
- `AppTimerCallback` / `PollTimerCallback` / `ExitDiagnosticModeAsync`：统一改为先置 `sendBusy = true` + 递增代次再启动任务；占用判断改用 `sendBusy`。
- `ClearSendTask(generation)`：按代次校验，只有当前登记的仍是本任务时才 `sendBusy = false; activeSendTask = null`，避免误清后续任务。
- 断线 / `Dispose` 时同时清 `sendBusy` 并递增代次，旧任务稍后完成不会误清新连接的任务。

### 2.3 #3 旧循环收尾破坏新事务

**根因**：`ProcessQueueAsync` 的 `finally` 无条件清 `loopActive/enterModeTask/active` 并调用 `ExitDiagnosticModeAsync`；末笔处理期间新请求入队会启动新循环，但旧循环的 `finally` 仍把共享状态清掉、恢复应用发送。

**修复**（`DiagnosticTransactionService.cs`）：

- 新增 `loopGeneration` 代次计数，`ProcessQueueAsync` 启动时记录 `myGeneration = ++loopGeneration`。
- `finally` 中只在 `loopGeneration == myGeneration`（仍是当前循环）时清理共享状态并恢复应用发送；代次已推进说明新循环已接管，旧循环直接返回、不动新事务状态。

### 2.4 #4 出队后等待进入独占的诊断跨断线重放

**根因**：请求在 `ProcessQueueAsync` 出队后、`RunTransactionAsync` 登记 `active` 之前，有一段 `await enterTask` 窗口；此窗口内断线时 `HandleConnectionStateChanged` 找不到该请求（`active` 为 null），清理不到它，重连后仍会发送 3C。

**修复**（`DiagnosticTransactionService.cs`）：

- 新增 `connectionGeneration` 连接代次；`ExecuteAsync` 入队时把当前代次绑定到 `PendingTransaction`。
- `ProcessQueueAsync` 出队后、执行前校验 `pending.ConnectionGeneration != connectionGeneration` → 直接返回 `Disconnected`，不发送 3C。
- `await enterTask` 之后再次校验连接代次，覆盖等待进入独占期间的断线。
- `HandleConnectionStateChanged` 断线分支 `connectionGeneration++`，使所有绑定旧代次的请求在出队后判为断开。

### 2.5 #5 接收路径硬截止检查

**根因**：`HandleDiagnosticPacket` 在回显匹配/响应完成时直接确认成功，仅依赖 10 ms 的 `InspectTimerCallback` 判超时，超过截止后到达的数据仍可能被误判成功。

**修复**（`DiagnosticTransactionService.cs`）：

- `HandleDiagnosticPacket` 进入后先取 `now = packet.ReceivedTimestamp`，判断 `now >= TotalDeadline` → 直接 `DeadlineExceeded` 失败。
- 回显匹配分支再判断 `now >= EchoDeadline` → 直接 `EchoTimeout` 失败，不确认回显。

## 3. 影响范围

**改动文件**（3 个）：

- `WpfApp1/Services/LinFrameChannel.cs` —— 接收分发与连接事件移出通道锁。
- `WpfApp1/Services/LinBusScheduler.cs` —— 新增 `sendBusy`/`sendGeneration`，发送出口生命周期改为代次管理。
- `WpfApp1/Services/DiagnosticTransactionService.cs` —— 新增 `loopGeneration`/`connectionGeneration`，队列收尾与连接代次约束，接收路径硬截止。

**未改动**（不影响）的模块：

- `LinFrameCodec`、`LinTransportProtocol`、`LinReadReplyParser`（诊断候选识别逻辑）、`DeviceInformationService`、`MotorCommandService`、`MotorStatusFrameParser`、`SerialPortConnectionService`、`CommunicationLogService`、`CommunicationLogEntry`、`MainWindowViewModel`、`ActuatorDebugViewModel`、`ActuatorDebugView.xaml`。
- 帧表、协议字节、校验算法、3C/3D 构帧、TP 重组规则、报文窗口显示均无变化。

## 5. 如何确保原有功能不受影响

1. **锁调整只改"持锁范围"，不改业务逻辑**：`HandleBytesReceived` 的判定条件（`isConnected && !disposed`）、`ConnectionStateChanged` 的状态写入（`isConnected`、`parser.Reset()`）逻辑不变，仅将回调触发移出锁外。
2. **发送出口语义等价**：`sendBusy` 与 `activeSendTask` 的组合完全覆盖原 `activeSendTask is not null` 的占用语义，且通过代次消除同步完成的竞态；应用 100 ms 轮询的"先 0x15 后 0x33、忙则跳拍"行为不变。
3. **队列与断线约束是新增防护，不改变正常路径**：`connectionGeneration` 只在断线时递增，正常连接下代次恒定，出队后校验恒通过；`loopGeneration` 只在收尾竞态时生效，正常单队列场景 `finally` 仍按原逻辑清理。

## 6. 如何确保后续诊断功能不受影响

1. **锁序定型为单向**：后续新增模块只需遵循"协调层锁 → 调度器锁 → 通道锁（叶子）"这一单向顺序，且不在任何锁内触发跨层回调，即可避免再引入死锁。
2. **发送出口的单一职责不变**：`sendBusy`/`sendGeneration` 是通用机制，OTA 等后续诊断阶段仍通过 `scheduler.SendDiagnosticRequestAsync` / `SendDiagnosticReadRequestAsync` 走唯一出口，无需了解代次细节。
3. **连接代次约束对 OTA 更关键**：OTA 阶段同样存在"出队后等待进入独占"的窗口，`connectionGeneration` 机制天然覆盖，后续无需重复设计。
4. **硬截止检查独立于定时器**：接收路径的截止判定不依赖 `InspectTimerCallback` 的 10 ms 节拍，后续新增诊断业务（超时参数不同）只要正确设置 `EchoDeadline`/`TotalDeadline` 即可复用。

## 7. 遗留说明

- 本轮修复未触碰 50 ms 组帧超时与诊断 20 ms 轮询节奏的组合边界（属既有机制组合风险，非本次引入的 bug），建议实机联调多帧响应时重点观察是否有丢段。
- 实机联调（3C 回显稳定性、Bootloader/硬件版本真实响应格式、失步恢复）仍为 pending，未随本轮修复改变。
